# i吃饭 · 功能对照说明

> 参考的是同类产品的**做法与维度**，不是视觉、文案或数据。所有店铺、评分、照片均来自用户手填，应用不请求任何平台接口。

## 参考来源与采纳点

| 参考对象 | 参考的做法 | 本项目的落地 | 差异 |
| --- | --- | --- | --- |
| 大众点评 / 美团 | 评分拆成口味、环境、服务等维度；收藏（想去）；按人均预算和场景筛店 | 四维评分 `ratings{taste,env,service,value}` + 兼容旧综合分；想去收藏夹；人均区间与场景标签 | 不抓平台榜单/评论/团购；不做店铺发现，只基于自己的历史记录 |
| 下厨房 | 用标签/食材描述菜品，按口味与食材找菜 | 口味/品类标签（辣、清淡、健康、高蛋白等）；忌口词表命中店名、品类、标签、备注 | 不做菜谱与食材库，只做"去哪家吃"的决策 |
| 薄荷健康 / Keep | 按减脂/增肌目标给热量与蛋白质目标，记录每日摄入 | 三档目标（减脂 1700/110、增肌 2300/140、保持 2000/100）；记录 kcal/蛋白；显示今日剩余与达标提示 | 数值是历史记录均值估算，明确"不构成营养或医疗建议"，不提供疾病饮食指导 |
| "今天吃什么"类决策工具 | 随机/转盘、避免连续重复、给主选与备选 | 时段感知 + 近 7 天重复降权（×0.25–0.85）+ 1 主推 2 备选；另有独立"手气抽签"按评分/新鲜度加权 | 推荐结果附中文理由；抽签展示权重表和随机数，可复核 |
| 聚会/投票类工具 | 按人数与预算给方案，多人对候选投票 | 2–3 个方案（总价/人均/场景理由/加餐）；投票清单 + 本机 +1 记票 | 不做多人实时投票（无后端），票数只在本机 |

## 本项目的差异点

1. **纯本地、零网络**：单文件双击即用；照片存 IndexedDB，记录存 localStorage；只有用户主动点"打开平台"才发生跳转。
2. **可解释**：每张推荐卡都列出价格、重复降权、口味命中、评分、场景匹配等理由，而不是黑盒排序。
3. **可复核的随机**：抽签给出候选数、权重表、总权重、随机数 r 与命中项，出现问题能复现。
4. **稳定性优先**：分页 30 条、图片懒加载、输入防抖、写盘哈希比对、`.bak`/`.raw` 容错、诊断面板。
5. **合规边界清晰**：不抓数据、不带渠道参数、不诱导刷评；营养为估算值。
6. **三类反馈不混用**：想去（收藏）、推荐反馈（喜欢 / 不想吃等）、真实到店（记录）各自独立落库，想去不等于到店，推荐反馈不写消费记录。

## 第一阶段：店铺档案与到店记录一体化

在现有店铺档案上增强，不另立店铺表；店铺仍由记录聚合，补充信息仍存 `fandazi.shopmeta`。

- **又来了**：档案页一键复用现有打卡流程（`quickEat()`），保存后记录 +1，不新建旁路记录。
- **重复店铺识别**：POI ID 相同优先；无 POI 时按「名称 + 地址」或「名称 + 200 米内坐标」退化；只给候选，**不自动合并**；可人工选择合并 / 标记同一家 / 不是同一家。合并只改店名与城市，历史日期、评分、金额、菜品、照片全部保留。
- **到店时间轴**：按日期倒序展示历次到店，点击复用现有记录详情。
- **人均与评分变化**：实际人均（实付总额 / 人数）与参考人均（手填 `perPrice`）分开统计，评分单独统计；无数据显示「暂无数据」，不估算、不互相填充。
- **统一反馈通道**：日常推荐 / 抽签 / 盲盒 / 旅行计划共用同一套反馈按钮与存储，`surface` 仅记录来源；想去只写 `wishlist`，反馈只影响排序，到店才写记录。
