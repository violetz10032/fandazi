# 跨设备投票 · 第二阶段三方案说明（供拍板）

> 依据：`sync-voting-design.md` 第 6 章 / 第 10 章、`sync-voting-implementation-spec.md` 第 6 章（核实时间 2026-11-05）。
> 现状：**方案 A 的「链接 + 回执 + 手动回填」已落地**，投票素材、编号候选图、二维码、手动回填、平票抽签、写回到店记录均可用。
> 本文只做三方案的取舍说明，不含代码改动。

---

## 方案 A：微信群投票素材生成（零后端）

**核心做法**
应用内选 3–8 家候选后，自动生成投票标题（如「周五晚 6 人 · 4 选 1」）、逐行编号的候选文案、1–8 号候选图、二维码与回填表；用户把文案/图片复制进微信群，或在「腾讯投票」小程序里手动粘贴标题与选项、设置匿名与截止时间后分享到群。群的投票结果由发起人在应用内向回填（逐家输入，或粘贴群接龙文本，本地正则解析编号），应用校验后排序、平票抽签，胜出店写回到店记录（`source=poll`）。
核实结论：腾讯投票与微信群投票**没有公开的创建/读取接口**，能自动的只到「素材生成 + 复制」，创建、发送、看票数、回填这四步必须人工；不抓取、不模拟登录、不调用非公开接口。

**用户操作成本**
- 发起人：选店（应用内完成）→ 复制文案 + 保存候选图 → 打开腾讯投票 → 逐项粘贴、设匿名与截止 → 分享到群 → 事后回填票数。**约 6–8 步，其中 4 步在微信里手工操作。**
- 参与者：在腾讯投票或群接龙里点选，**无需安装、无需账号、无需 GitHub**，成本最低。

**实现复杂度**
低。素材生成、编号图、二维码、接龙解析都是本机纯前端逻辑，复用现有候选卡与排序/抽签；无服务端代码。回填校验只需「总票数 ≤ 参与人数 × 候选数」这类本地规则。

**是否需要额外基建**
不需要。零服务器、零数据库、零备案、零费用；数据不出本机，天然离线可用。

**主要风险**
- **无实时**：票数必须人工回传与回填，异地朋友无法直接参与，容易「投了没回填」。
- **无防刷**：腾讯投票结果无法校验，接龙文本可伪造；只适合信任圈，不适合公开评选。
- **体验断点**：候选图与文案要跨 App 搬运，店名、价格在微信里仍需用户目视核对，仍可能漏项。
- **依赖第三方形态**：腾讯投票的入口与交互随时可能调整，只能跟着改文案说明。

## 方案 B：应用内投票房间（轻后端）

**核心做法**
把「房间」搬到自己的服务上：发起人创建房间，得到房间码/链接（或二维码），群里点开即进入 H5 只读候选页，参与者选「想去 / 无所谓 / 不想去」（或 1–5 分）后提交，服务端按 `voterId` 去重、实时计票；发起人页面直接看到汇总，截止后一键结算并写回记录。身份走「匿名设备码 + 12 位恢复码」方案，不收集手机号/邮箱；数据境内存储（推荐腾讯云开发 CloudBase，境内节点、匿名登录、数据库 + 实时 + 存储 + 云函数一套齐）。

**用户操作成本**
- 发起人：应用内选店 → 生成房间链接/二维码 → 发到群 → 看实时票数 → 结算。**约 3–4 步，全部在应用内完成。**
- 参与者：点链接 → 选题 → 提交，**仍需安装？不需要**；但首次进入可能需要一个极短的身份/昵称步骤（可跳过）。

**实现复杂度**
高。客户端需新增约 1,100–1,300 行（加密载荷、房间状态机、离线队列、冲突合并、同步卡片 UI），服务端需建表（`devices` / `share_rooms` / `candidates` / `votes` / `sync_changes`）、云函数、权限规则、限流与幂等；还要做弱网与离线重试。

**是否需要额外基建**
需要。云数据库 + 云函数 + 对象存储 + 实时通道；默认域名可直接用，但绑定品牌域名需 ICP 备案，上架 App 还需 App 备案；隐私政策需按个人信息清单逐项声明，并准备删除/导出通道。

**主要风险**
- **合规成本**：一旦有服务端，就落入个人信息处理与 UGC 范畴，需要隐私政策、数据删除通道、内容审核与安全评估；这是长期负债，不只是开发工作量。
- **公开链接风险**：房间链接可被转发，需要截止时间、人数上限（50 条回执）、可撤销与只读降级。
- **运维与成本**：可用性、备份、限流、账单全部自己承担；实时监听容易放大费用。
- **防刷仍不彻底**：匿名身份只能做到「同一 voterId 取最新」，做不到强身份校验。

## 方案 C：微信小程序

**核心做法**
把「投票房间」做成微信小程序（建议原生 WXML/WXSS/JS，只做投票这一小块），利用小程序在群里的天然入口（聊天工具模式 / 群工具）降低参与门槛；页面走预设标题模板，只展示店名与序号，尽量不做自由文本，避免被判为社交-社区类目。现有单文件 `index.html`（原生 JS + DOM + localStorage/IndexedDB）**不能直接迁入**：小程序没有 DOM，也没有 localStorage/IndexedDB；可复用的是纯函数（迁移、去重、评分、排序抽签、分享包编解码），预估业务逻辑复用 30–50%，UI 与存储 0%。

**用户操作成本**
- 发起人：在小程序里选店（或从应用同步候选）→ 生成小程序码/房间 → 发群。
- 参与者：群内点开小程序卡片 → 直接投票，**体验最顺、无需跳浏览器**；但需要接受微信授权（昵称/头像可最小化）。

**实现复杂度**
很高。需要新主体资质、新工程、新存储层（云数据库）、新分享层（`#share=` 链接 → 小程序页面路径/小程序码），并维护 H5 与小程序两套视图；审核与备案周期预估 **2–6 周**（认证 1–5 个工作日、小程序备案平台初审 1–2 个工作日 + 管局 1–20 个工作日、代码审核 1–7 天）。

**是否需要额外基建**
需要。企业或个体工商户主体（**个人主体不能做投票类目**）、微信认证（个体 30 元 / 企业 300 元每年）、小程序备案、HTTPS 且已 ICP 备案的服务器域名、云开发/云数据库环境。

**主要风险**
- **资质门槛**：个人主体直接不可行；企业主体需类目匹配，含 UGC 会被要求社交类目与额外资质。
- **审核风险**：类目不符、功能不完整、诱导分享、UGC 未审核、隐私指引缺失都是常见驳回原因。
- **双端维护**：小程序 + H5 + APK 三套视图，长期维护成本显著上升。
- **收益不确定**：只有在「群投票」确认为高频刚需、且用户量达到阈值时，才值得承担上述固定成本。

## 对比一览

| 维度 | A. 微信素材生成（已落地） | B. 应用内房间 | C. 微信小程序 |
| --- | --- | --- | --- |
| 参与者是否需要账号 | 不需要 | 不需要（匿名设备码） | 需要微信登录/授权 |
| 实时性 | 无（人工回传） | 有（实时/近实时） | 有 |
| 发起人操作步数 | 6–8 步（4 步在微信内） | 3–4 步 | 3–4 步 |
| 实现复杂度 | 低 | 高（客户端 1,100–1,300 行 + 服务端） | 很高（新工程 + 双端） |
| 额外基建 | 无 | 云数据库 / 云函数 / 存储 / 实时通道 | 主体资质 + 认证 + 备案 + 云环境 |
| 费用 | ¥0 | 早期 ¥0–50/月，量大按量 | 认证 30–300 元/年 + 云资源 |
| 合规负担 | 无（数据不出本机） | 中（个人信息、UGC、删除通道） | 高（PIPL + 平台类目 + 备案） |
| 上线周期 | 已完成 | 数周开发 + 合规准备 | 2–6 周资质与审核，另加开发 |
| 主要风险 | 无实时、无防刷、体验断点 | 合规与运维长期负债、公开链接风险 | 类目/审核驳回、双端维护、个人主体不可行 |

## 建议顺序

1. **先停在 A**：零成本验证「多人一起选」是否真是高频场景；当前版本已具备完整闭环。
2. **确认高频且要求实时，再做 B**：境内云开发起步，先只做「房间 + 计票」，同步与照片上云后置。
3. **C 只在满足阈值时做**：已有企业与个体工商户主体、明确要在微信群内一键参与、且能承担 2–6 周备案审核与双端维护。个人主体不要启动 C。
