# i吃饭 · fandazi

记录吃过的店，按场景、时间与距离决定下一顿。

单页应用，**零构建、零依赖、零 CDN、零后端**；所有记录、评分、照片只存在你自己的设备上，不抓取任何平台数据。

**在线使用**：<https://violetz10032.github.io/fandazi/>（HTTPS，可直接安装为桌面/手机应用）

---

## 是什么

吃饭这件事有三个高频问题：去过哪家、这次吃什么、一群人吃什么。i吃饭把它们放进一个本地应用：

- **记录**：店名、商圈、人均、人数、四维评分（口味 / 环境 / 服务 / 性价比）、口味标签、忌口、营业与适合时段、手填距离与出行耗时。
- **推荐**：日常（1 主推 + 2 备选，附中文理由）、聚会（2–3 个方案含总价与人均）、健身（按热量/蛋白目标汇总）、朋友（可复制推荐文案）。
- **多人聚餐**：建活动（日期时间、人数、人均预算、区域/半径）+ 参与者忌口硬过滤 → 3–8 个候选（中文理由 + 谁能吃）→ 生成跨设备投票链接 / 二维码 → 回执或手动回填票数 → 一键结算只锁定结果，确认到店后才写入一条聚餐记录。
- **抽签**：价格区间内按评分与新鲜度加权随机，权重表与随机数可复核。
- **地图**：无底图散点图，按记录里的经纬度本地投影；点大小/颜色表达到访或评分，无坐标的店单独列出、绝不编造位置。
- **分享**：1080×1350 分享图、长图、CSV/JSON/文本导出，以及与好友的 `.fanzi.json` 本地互导。
- **第一次使用**：记录为空时不出现空白页，直接给出「记第一家店」「从链接 / 分享包导入」「看示例（只预览不写入）」三条路径。

## 技术形态

| 项 | 说明 |
| --- | --- |
| 实现 | 原生 HTML + CSS + JavaScript，**全部内联在 `index.html`** 一个文件里 |
| 数据 | 结构化数据存 `localStorage`（主库 `fandazi.v2` + 增量键 `fandazi.shopmeta` / `fandazi.trips` / `fandazi.feedback` / `fandazi.favorites` / `fandazi.pantry` / `fandazi.cooklog` / `fandazi.recipes` / `fandazi.homefb` 等），照片压缩后存 `IndexedDB`，均在本机 |
| PWA | `manifest.webmanifest` + `sw.js`，仅缓存同源静态资源 |
| 网络 | 默认只在你主动点击外链（美团 / 大众点评 / 高德 / 百度地图搜索）时新开窗口；可选的外部请求只有「高德图层」：网页版按需注入官方 JS API，APK 内改为加载 Pages 上的 `map-embed.html`（iframe），失败自动回落画布 |
| 定位 | 仅在用户点击「用当前位置」时取一次位置；有坐标的店按 Haversine 实算距离，无坐标仍用手填估算（见下文「定位与距离」） |
| 地图 | 默认是 Canvas 2D 无底图散点（等距圆柱投影 + `cos(平均纬度)` 修正），不申请 Key、不发外部请求；可选「高德图层」使用官方 JS API 2.0 底图（见下文「可选高德底图」） |
| 兼容 | v1/v2 旧数据自动迁移到当前数据版本（v3） |

## 跨设备投票（首版）

聚餐活动详情里点「生成投票链接」，即可把候选店发到群里，参与者不用安装应用、不用账号：

- 链接形如 `https://…/index.html#poll=pv1.<base64url(gzip(JSON))>`，只含候选编号、店名、城市、商圈、人均；**不含备注、精确地址、记录 ID 或设备信息**。总长超过 4096 字符时自动退回「编号清单 + 手动回填」；链接也可直接展示为二维码。
- 参与者打开后是只读页，逐店选择「想去 / 无所谓 / 不想去」，生成 `VR1|…` 回执文本或 `#votereceipt=vr1.` 回执链接发回群里。
- 发起人把一条或多条回执粘回活动详情，按随机 `voterId` 去重取最新后汇总；回执与手动票数二选一，回执生效时手动票数被忽略，可随时「改回手动票数」。
- 上限 50 条回执；活动日期当天 23:59 后链接只读；页面标注「朋友局，无签名校验」，不承诺防刷。
- 本版**未包含**：实时同步、服务端计数、身份校验、投票结果加密。
- 网页端需 HTTPS 才能把链接分享给别人（`file://` 下会提示改发编号清单）；APK 内生成链接时固定使用线上 Pages 地址。

## 盲盒吃啥（首页悬浮球）

- 首页右下角「🎲 帮我选」悬浮球，可拖拽并吸附到左/右边缘；位置记在本机，不遮底部导航，离开首页自动隐藏。
- 不新写第二套算法：复用抽签页的价格区间与加权权重（`buildDrawPool` + `storeWeight`），黑名单、忌口、菜系拉黑、永久排除照旧生效。
- 结果卡：店名、菜系/标签、**参考**人均、距离（只按坐标实算，无坐标显示「暂无数据」，不估算）、一句话理由（复用现有推荐解释）。
- 「就吃这家」只打开预填的记录草稿（店名 / 城市 / 参考人均），必须点「保存」才写入，不会直接落库或污染统计；「换一个」只在本次会话内临时排除当前店；「导航前往」复用现有高德跳转。
- 摇一摇：仅 Android，带阈值与 1.5s 冷却；**检测不到可用加速度事件时隐藏摇一摇开关**，不留点了没反应的入口。定格时 `navigator.vibrate([30,50,30])`，APK 已补 `VIBRATE` 权限；不支持时静默跳过。
- 本版**未包含**：iOS `DeviceMotionEvent.requestPermission` / Safari 适配；摇一摇在 Android WebView 内是否可用需真机验收，测不到时只保留悬浮球入口。

## 智能粘贴 + 极速速记草稿

**智能粘贴（只做「直接粘贴」入口）**

- 添加店铺页（快速 / 完整记录表单）有可折叠的「智能粘贴」多行文本框，提示「把大众点评 / 高德 / 小红书的分享文案粘到这里」。
- 粘贴（`paste`）立即解析，`input` 防抖 420ms 解析，另保留「解析」按钮；文本框为空时点解析只提示「先粘贴一段文案」。
- **不读取剪贴板**：不调用 `navigator.clipboard.readText()`、不申请任何剪贴板权限、不做权限绕行。
- 纯前端正则识别：店名（「」/『』/《》/引号内文字，或剔除 `【大众点评】`「我在高德地图发现…」等平台前后缀；普通句子一律不猜）、人均（`人均 [:] ¥120` / `¥120` / `120 元/人`）、商圈（`XX区` / 商场 / 广场 / 地铁站）、地址（路 / 街 / 大道 / 巷 / 弄 + 门牌号，优先带「号」的整条）。
- 未识别字段一律留空，不补默认值；已有内容的字段不覆盖。已填入时标注「来自粘贴解析」。
- 人均只写入「参考人均」，**绝不写入实付（总价）**。

**极速速记草稿**

- 快速 / 顺手记表单底部有「存草稿」：只填店名（可带一张照片）即可存下。
- 草稿独立存 `fandazi.drafts`（本机），**不进记录列表、不进统计、不进年度报告**；带创建时间戳与当次已有定位（没有定位就留空，不额外申请权限、不编造）。
- 记录页顶部可折叠「待完善草稿 (N)」，展开后逐条「补完 / 删除」。
- 「补完」复用同一套记录表单并标注「来自速记草稿」，补完四维评分后点保存才转为一次真实到店记录（此时草稿自动出列）。
- 草稿不参与备份包（避免把半成品混进完整备份）。

## 抽签疲劳冷却 + 时段加权 + 15% 探索

- **疲劳冷却**：读 `fandazi.v2.visits` 的最近 7 天足迹（不读 `trips`，那是旅行计划）。48 小时内去过的店权重置 0；24 小时内吃过同一菜系，该菜系所有店权重 ×0.3。
- **空候选兜底**：筛空后先放宽 48 小时冷却、再放宽同菜系削减，并在结果里明示「已忽略 XX 规则」，绝不给空白结果。
- **时段情境**（本地时间）：工作日 11:30–13:30 提高人均 20–40 / 适合午餐 / 800m 内；周五 17:30 后与周末提高高评分与烧烤火锅聚餐类；21:30 后优先夜市 / 大排档 / 烧烤标签。**没有营业时间数据，只按菜系与标签推，不会声称「正在营业」**；无坐标店在距离维度按中性处理（不加不减）。
- **15% 探索**：固定 15% 从「想去但从未到店」池里抽，仍然遵守黑名单、忌口、菜系拉黑、预算与价格区间；池子为空时回落到正常加权。收藏是独立状态，不并进想去池；只有同时标记了「想去」的店才进入探索池。
- **硬规则优先级不变**：黑名单 > 忌口 / 排除 > 手动口味 > 画像 > 评分与情境加权。每条规则的加减分都会写进结果区的推荐理由。

## WebDAV 云备份与还原

- 位置：**我的 → 本机数据 → WebDAV 云备份**（可折叠面板），填写服务器地址（指向网盘里的一个文件夹）、用户名、应用独立密码、备份文件名（默认 `fandazi_backup.json`）。
- **网页版如实受限**：浏览器跨域（CORS）会拦截 WebDAV 的 `PROPFIND` / `PUT`，面板保留入口并明确提示「建议在 APK 内使用」，不绕行、不走代理。
- **APK 内走原生 HTTP**：直接调用 CapacitorHttp（不启用它的全局 fetch 补丁，因此不影响高德 JS API 动态加载与 Gist 同步），不受浏览器跨域限制。
- **复用现有完整备份**：上传就是把「完整备份」对象原样 `PUT`（`format` / `schemaVersion` 8 / SHA-256 校验值全部沿用），没有另造格式；上传成功会同步「上次备份」时间与体积。
- **拉取还原**：`GET` 回来后走现有 `parseBackupText` + SHA-256 校验，再进入现有的「合并 / 完整替换」恢复弹窗（含恢复前自动恢复点）。
- **测试连接**：`PROPFIND` 只读探测目录，状态码翻成人话——401 密码或用户名错（坚果云需「应用独立密码」，不是登录密码）/ 403 权限或路径不对 / 404 目录或文件不存在 / 405 不是 WebDAV 地址 / 409 父目录缺失 / 507 空间不足 / 超时或 HTTP 0 多为跨域被拦。
- **密码只存本机**：写在 `localStorage`（`fandazi.webdav`），界面明说「未加密，建议使用应用独立密码」，可一键「清除本机口令」。

### 数据同步边界（哪些能同步、哪些只能靠备份文件搬）

| 数据 | Gist / Contents 增量同步 | WebDAV / 完整备份整包 | 说明 |
| --- | --- | --- | --- |
| 到店记录 + 照片 | ✅ 同步 | ✅ 整包 | 唯一走增量同步的数据 |
| 想去清单 `db.wishlist` | ❌ 不同步 | ✅ 整包 | 只能靠完整备份文件跨设备搬 |
| 收藏 `fandazi.favorites` | ❌ 不同步 | ✅ 整包 | 独立收藏夹，不并入想去，也不单独开云同步 |
| 地点 / 设置 / 投票 / 报告 / 抽取记录 | ❌ 不同步 | ✅ 整包 | 同上 |
| 在家吃 `fandazi.recipes` / `fandazi.homefb` / `fandazi.pantry` / `fandazi.cooklog` / `fandazi.homeweek` / `fandazi.cookprog` | ❌ 不同步 | ✅ 整包 | **不单独开云端同步**；本阶段没有为烹饪数据新增 Gist / Contents / WebDAV 字段或接口 |
| 店铺补充信息 / 旅行 / 菜品库 | ❌ 不同步 | ✅ 整包 | 同上 |

- **Gist / Contents** 只搬运「到店记录 + 照片」；它们不会读取也不会写入上表中的其他键。**烹饪数据（`fandazi.recipes` / `fandazi.pantry` / `fandazi.cooklog` / `fandazi.homefb`）明确不进入 Gist / Contents 增量同步**，只随完整备份整包搬运。
- **WebDAV** 不是增量同步，而是把「完整备份」JSON 整包上传 / 拉取；整包天然包含上表全部数据（含在家吃数据），但**没有**为烹饪数据扩展任何独立同步字段。网页版受 CORS 限制时，仍可用「导出 / 导入完整备份」文件搬运。
- **只能靠备份文件搬**：想去、收藏、地点、设置、投票、在家吃数据、店铺补充信息 / 旅行 / 菜品库。换设备或清浏览器数据前，请先导出完整备份；旧备份缺少收藏段时恢复**不会清空本机收藏**，缺在家吃段（含一周菜单 `week` / 烹饪进度 `cookprog`）同样保持本机现状。

### 本机备份的三层边界（自动备份 / 恢复点 / 完整备份）

| 机制 | 存在哪 | 含什么 | 不含什么 | 什么时候消失 |
| --- | --- | --- | --- | --- |
| 自动备份（**默认关闭**；开关打开后每 24 小时一次，且只在明确操作后空闲时写） | 网页：IndexedDB `fandazi.backups`；APK：应用私有目录 `fandazi-backups`（另在本机 IndexedDB 留一份可读副本） | 记录与配置整包 + 照片**引用** | **照片本体**（照片只在 IndexedDB） | 清理站点数据 / Android「清除数据」/ 卸载 App |
| 恢复点（导入、恢复、清空照片前自动建，保留最近 2 份） | IndexedDB `snapshots` | 当时的记录与配置 | **照片本体**（只存 `photoId` 引用；照片被清理后恢复点也找不回） | 下一次导入会覆盖最旧的一份 |
| 完整备份（手动导出 `.fanzi.json` / 上传 WebDAV） | 你自己的下载目录 / 网盘 | 记录、配置，**可选是否内联照片 base64** | — | 只要文件还在就一直可用 |

- **APK 内自动备份目录在文件管理器里看不到**：`fandazi-backups` 是应用私有目录（系统限制，正常现象），不申请存储权限、也不写 `Android/data`。要把备份取出来，请用「我的 → 本机数据 → 导出备份到手机目录」，在弹出的系统面板里另存或发给自己。
- **照片要跟着走，必须用完整备份**：自动备份与恢复点都只存引用；换机或清数据前，请在完整备份里勾选「包含照片」。
- **启动阶段不做任何文件系统操作**：`init()` / 首屏渲染期间不调用 `Filesystem` / `Share` 等原生桥接；自动备份的启动检查被移除，改成「开关打开 + 你有明确操作（首次点按、保存记录、进入本机数据页）之后才检查一次」。
- **自动备份默认关闭**：开关在「我的 → 本机数据 → 启动时自动备份（仅应用内）」，默认关；关着时启动阶段与后台都不会读写私有目录。手动「立即备份」不受开关影响，始终可用且只写应用私有目录。
- **照片本体不进自动备份**：自动备份只含记录与照片引用，照片本体仍在 IndexedDB，需用完整备份带走。
- **Android 系统云备份**（`allowBackup`）保持开启，用于换机时由系统代为搬运；它属于操作系统行为，不是本应用上传。不需要可在系统设置里关闭该应用的云备份。

## AA 分账与复古票根

- **AA 分账**：入口在「记一餐」表单（按当前总额 / 人数预填）和每条记录的卡片上。弹窗填总额、人数、其中酒水等额外费用（已含在总额）、几人不分摊酒水；输出「分摊酒水的人 / 不含酒水的人 / 发起人」三档金额。
  - 金额以分为单位计算，**各人相加恒等于总额**；除不尽默认向上取整到角，取整差额计入发起人；可勾选抹零到元，抹掉的差额同样由发起人承担，并在结果里写明金额。
  - 可一键复制微信收款文案，弹窗内同时提供只读文本框可长按手动复制；**算出的金额只进文案，不写入记录实付**。
- **复古票根海报**：在现有分享图弹层新增「复古票根」模板（纯 Canvas 2D，无第三方库、无外部请求）。
  - 1080×1620：顶部拍立得白边 + 美食照（自动取该店最近一次带照片的记录，无照片时画占位插画）、店名与商圈、日期生成装饰条形码与票号、四维评分旋转半透明印章、「必吃推荐 / 值得一试」大印章、底部虚线撕票口与锯齿撕边。
  - 导出复用现有「保存 PNG / 系统分享」通路；「复制图片」为附加项，浏览器不支持时提示改用「保存图片」，不会报错中断。
  - 同一弹层内可在「推荐海报（1080×1350）」与「复古票根（1080×1620）」之间来回切换。

## 本地运行

```bash
git clone https://github.com/violetz10032/fandazi.git
cd fandazi
python -m http.server 8765
# 打开 http://localhost:8765/index.html
```

三种打开方式的差别：

| 方式 | 能做什么 | 不能用什么 |
| --- | --- | --- |
| 双击 `index.html`（`file://`） | 记录、推荐、抽签、导出、分享图全部可用 | Service Worker、安装到桌面、浏览器通知 |
| 本地静态服务器（`http://localhost`） | 以上全部 + 安装 + 离线 + 更新提示 | — |
| HTTPS 静态托管（如 GitHub Pages） | 完整的 PWA，手机也可安装 | — |

> `http://` 局域网 IP（如 `http://192.168.x.x:8765`）不是安全上下文，浏览器会禁用 Service Worker 与安装入口。手机安装请用 HTTPS 部署。

### 本地自动化测试（headless Chrome）防坑：可能触发 Windows 登录失败并锁账户

本地 CDP 测试会启动无头 Chrome。若每次测试都用 `%TEMP%` 下带时间戳的一次性 `--user-data-dir`，Chrome 的凭据/扩展初始化会反复触发 Windows 集成认证失败；短时间累计 10 次即可能把当前账户锁 10 分钟（表现为「电脑崩溃/重启」）。必须遵守：

- **固定 profile + 单实例复用**：统一走 `.tmp/cdp-harness.js`，每个套件用固定目录 `.tmp/profiles/<suite>`（p0 / back / p1 各自独立，不共用同一个 profile 同时跑），**跑前清空、跑后 teardown 删除**；测试进程内只 `ensureBrowser()` 一次，套件之间开新标签页隔离，不要反复 `launch`。
- **禁用扩展与后台组件**：启动参数包含 `--disable-extensions`、`--disable-component-extensions-with-background-pages`、`--disable-features=MediaRouter`、`--disable-sync`、`--disable-background-networking`（迅雷等 BHO 扩展 `xl_ext_chrome.exe` 会被疑似触发凭据重试）。
- **禁止常驻**：每个脚本结束必须 `Browser.close()` 并确认 CDP 端口关闭，不留常驻进程/端口。
- **启动前与运行中做只读锁定检测**：用 `OpenInputDesktop` 判断当前是否在安全桌面（锁屏 / 全屏 UAC），命中就中止，不要叠加启动；不要用 `LogonUI` 进程判断（解锁后它可能残留，会误报）。
- **临时 profile 必须 teardown**：跑完立即删除本套件的 `.tmp/profiles/<suite>`（历史遗留 `%TEMP%\fz-*` 也要在确认后清理），否则一次几百 MB、几十次就是 GB 级垃圾。

### 导出与分享（v1.0.1 起已支持）

APK 内接了 `@capacitor/filesystem` + `@capacitor/share`：**CSV / JSON / 文本导出、分享图、长图、好友 `.fanzi.json` 分享、巡店清单分享**都会先写入应用缓存目录（`Directory.Cache`），再调起系统分享面板；在面板里选「保存到文件 / 下载」即可落到 Android 下载目录，也可以直接发给微信等应用。

实现方式（`index.html` 里的“Capacitor 原生桥接”一段）：

- 能力探测用 `window.Capacitor.isNativePlatform() === true`，并确认 `Plugins.Filesystem`、`Plugins.Share` 存在；**不看 UA**。
- 原生分支：`Filesystem.writeFile({ directory:'CACHE' })` → `Filesystem.getUri()` → `Share.share({ files:[uri] })`；纯文本走 `Share.share({ text })`。
- 网页版分支：仍然是原来的 `<a download>` + Blob 与 `navigator.share`，**代码路径原样保留**，行为与 v1 一致。
- 用户取消分享面板（cancel）不报错也不弹失败提示；真失败会 toast 写明原因，并记到「我的 → 诊断」错误日志。

| 操作 | 网页版 / 在线地址 | APK（WebView） |
| --- | --- | --- |
| 导出 CSV / JSON | 浏览器直接下载到下载目录 | 分享面板 → 手动选「保存到文件/下载」 |
| 保存分享图 / 长图 | 直接下载 PNG | 分享面板 → 保存或直接发给别人 |

### 系统返回键（v1.0.2 起已接管）

APK 内接了 `@capacitor/app`（6.0.3），Android 的物理/手势返回键不再直接退出，而是复用网页版的返回层级：

- **有弹层**：先关最上层弹层（分享 / 导出 / 教程 / 照片预览等，按 z-index 取最上层，同层取后开的）；
- **在子视图**：从日历 / 地图 / 聚餐等面板退回列表或「今日推荐」；
- **都在最外层**：才调用 `App.exitApp()` 退出应用。

实现要点（`index.html` 的「返回层级」一段）：

- 能力探测：只有 `window.Capacitor.isNativePlatform() === true` 且 `Plugins.App.addListener` 存在时才绑定；网页版 / 无插件环境下完全不注册，继续走原来的 `history` + `popstate` 分支，行为与之前一致。
- 防双触发：原生 `backButton` 若与 WebView history 同一次手势都触发，用 400ms 时间窗只执行一次（`nativeBackAt` 标记），不会连退两级。
- 守卫回收：原生返回关掉一层后调用 `syncBackGuard()`，与网页版的 history 守卫状态保持同步。

**未真机验证**：本机没有 Android SDK/模拟器，这一条只做了代码静态检查与云端编译；物理返回键的实际手感、双击退出、以及各机型手势返回的差异需要在装机后确认（见下面自测清单）。

### 运行形态与限制

- WebView 加载的是**打包在 APK 里的本地资源**（`assets/public`），首次打开不需要联网，数据同样只存在本机 WebView 的存储里。
- 已确认 APK 内包含 `assets/public/index.html`、`icons/`、`manifest.webmanifest`、`sw.js`；资源全部是 `./` 相对路径，因此在 `file://`、WebView 本地资源、GitHub Pages 子路径下都能找到图标与清单。
- FileProvider 用 `${applicationId}.fileprovider`（`com.fandazi.app.fileprovider`），`file_paths.xml` 已覆盖 `cache-path`、`files-path`、`external-path`，与 Share 插件读取的文件 URI 一致。
- Service Worker 在 Capacitor 默认的 `https://localhost` 源下是可选的：注册失败只会在「我的 → 诊断」里记一条日志，不会白屏（页面是纯静态资源）。
- **仍需真机确认的部分**：本机没有 Android SDK/模拟器，所以“导出→分享面板→保存到下载”这一条链路只做了静态检查与云端编译，**没有在真机点过按钮**。装机后请按下面的自测清单走一遍。
- APK 与在线 PWA 是**两份独立的数据**：APK 里的记录不会同步到网页版，反之亦然。想迁移就用「我的 → 数据 → 导出 JSON」再在另一侧导入。

### 桌面图标切换（Android，实验性，默认关闭）

- **做法**：`MainActivity` 不再直接挂 `LAUNCHER`，改由两个 `activity-alias` 提供桌面入口——`.MainActivityA`（定位碗，`android:enabled="true"`）与 `.MainActivityB`（城市一碗，`android:enabled="false"`）。两者都指向 `MainActivity`，只改 alias 的启用状态，不动 Activity 本身。
- **原生插件**：`android-app/android/app/src/main/java/com/fandazi/app/IconAliasPlugin.java`，通过 `PackageManager.setComponentEnabledSetting(..., DONT_KILL_APP)` 切换，并在 `MainActivity.onCreate` 里 `registerPlugin()` 注册。
- **入口**：APK 内「我的 → 图标风格 → 桌面图标」，只有 `Capacitor.isNativePlatform()` 且 `Capacitor.Plugins.IconAlias` 存在时才显示；网页 / PWA / 旧 APK 自动隐藏，不留死按钮。**默认是 A，用户主动点击才切换。**
- **顺序与回滚**：先启用目标 alias → 校验确实已启用 → 成功后才禁用旧 alias；任一步抛错立即把 A 启用、B 禁用，并提示「切换桌面图标失败，已回滚到 A（定位碗）」。
- **风险（设置页同步展示原文）**：切换桌面图标后，部分桌面会移除原有快捷方式，需要重新添加；部分机型可能不生效。升级到本版时，系统记录的旧快捷方式也可能失效，需要重新添加。
- **验证状态（如实）**：本机没有 JDK / Android SDK / 真机，无法做运行期验证。已在 GitHub Actions 完成编译，并在构建产物上校验合并清单：两个 `activity-alias` 都存在、带 `MAIN` / `LAUNCHER`、A `enabled=true`、B `enabled=false`、`targetActivity` 指向 `MainActivity`、B 引用 `ic_launcher_b`（见工作流「校验启动入口与双图标资源」步骤）。注：`aapt` / `aapt2` 的 `badging` 不会把 `activity-alias` 报成 `launchable-activity`，所以启动入口以清单结构为准。**实际点击切换、各桌面/ROM 的表现仍未经真机验证**。
- **PWA / 网页版无法切换启动图标**（系统限制），固定 A；只有 APK 提供桌面图标切换。
- **万一桌面没有图标**：应用仍已安装，可从系统设置「应用 → i吃饭 → 打开」进入，或在电脑上执行 `adb shell pm enable com.fandazi.app/com.fandazi.app.MainActivityA`；卸载重装也会回到 A。

## 定位与距离

距离有两种来源，界面始终分开标注，不混为一谈：

| 来源 | 什么时候有 | 界面写法 | 参与筛选 / 排序 |
| --- | --- | --- | --- |
| 定位计算 | 店铺记录里有经纬度，且你点过「用当前位置」 | `距我约 0.5 km（定位）` | 是（按坐标实算） |
| 手填估算 | 记录里填了「距离 km」，但没有店铺坐标 | `距我约 1.5 km（手填）` | 是（按手填值） |
| 都没有 | 既没坐标也没手填 | 不显示 / 「未填距离」 | 否 |

### 怎么用

1. 「今天吃什么」的筛选区点 **用当前位置** → 允许授权后显示 `已定位（±20m，17:53）· 有坐标的店按真实距离`；旁边的 **清除定位** 可恢复全部手填。
2. 记一餐 / 编辑记录时，在「经纬度 lng / lat」下方点 **用当前位置填入店铺坐标**。这里写入的是**店铺坐标**，不会覆盖「我的位置」缓存（否则距离基准会变成店铺自身）。
3. 有坐标的店用 Haversine（球面距离，R=6371.0088 km）实时计算，保留 1 位小数；没坐标的店继续用手填的 km，并标注「手填」。

### 权限与环境

| 环境 | 能否定位 | 行为 |
| --- | --- | --- |
| HTTPS（GitHub Pages） | 可以 | 首次点击弹系统授权 |
| `http://localhost` / `127.0.0.1` | 可以 | 本地调试等同安全上下文 |
| `http://` 局域网 IP | 不可以 | 中文提示「不是安全上下文」，回退手填，不白屏 |
| 双击 `file://` 打开 | 不可以 | 提示当前环境无定位接口，回退手填 |
| APK（Capacitor WebView） | `GeoPermission` 原生插件做显式运行时申请（本版 APK），**真机未验证** | 点击后先 `check` 再按需 `request`；拒绝 / 永久拒绝 / 服务关闭各有中文提示与「去系统设置」入口，失败自动展开手填 |

- **Capacitor 确实会代申请，但不够用**：`BridgeWebChromeClient.onGeolocationPermissionsShowPrompt`（`node_modules/@capacitor/android/.../BridgeWebChromeClient.java`）在 WebView 请求定位且未授权时会 `permissionLauncher.launch(new String[]{COARSE, FINE})`，拉起系统权限框，授权后 `callback.invoke(origin, true, false)` 放行；`Bridge.java` 里还有 `settings.setGeolocationEnabled(true)`。所以「Capacitor 完全不管权限」的说法不成立。
- **那为什么实测还是取不到**：它只在 WebView 真正发起定位时才触发，且**不检查系统定位服务开关**、**不区分「本次拒绝」与「永久拒绝」**、**没有跳转设置的能力**；更关键的是旧包 `AndroidManifest.xml` 只声明了 `INTERNET`——未在清单声明的权限系统会直接判为拒绝且**不弹窗**，WebView 回调拿到的就是拒绝，JS 侧只看到 code 1。另外「不再询问」已勾选、系统定位关闭、室内高精度超时，这几种在旧 UI 里都表现为同一句「定位失败」，用户无从下手。
- **现在的做法**：新增原生插件 `GeoPermissionPlugin`（`@CapacitorPlugin(permissions = location → COARSE + FINE)`）暴露 `check / request / openAppSettings / openLocationSettings`。`check` 返回 `{state, precise, service, canAsk, requested}`，`state` 取 `granted / denied / denied_permanent / service_off`：已授权直接定位；本次拒绝发一次系统申请；永久拒绝（申请过且 fine/coarse 都无 rationale）不再弹窗，直接给 `设置 → 应用 → i吃饭 → 权限 → 位置` 的完整路径；`service === false` 时给 `设置 → 位置信息（定位）` 并显示「去开启定位」。三种失败都保留「手动填起点」。
- 界面按钮：失败时筛选区出现「去系统设置」（永久拒绝 / 本次拒绝）或「去开启定位」（服务关闭），点击即跳对应系统页面；定位成功后按钮自动隐藏。
- 单测（Web 层打桩模拟原生插件）：`.tmp/geo-permission-test.js` 覆盖授权成功、本次拒绝、永久拒绝、定位服务关闭、网页版无插件回退，**7/7 通过**（`CDP_PORT=9245 node .tmp/geo-permission-test.js`）。
- 只在点击按钮时取一次位置（先 `enableHighAccuracy:true` / 12s，超时后自动降精度再试 6s），**不后台持续定位、不做轨迹**。
- 位置缓存在 `localStorage` 的 `fandazi.geo.last`（`{lat,lng,acc,at}`，坐标保留 5 位小数），只存本机、不写入记录、不上传。
- 拒绝授权（code 1）、超时（code 3）、定位不可用（code 2）、无定位接口都有对应中文提示，按钮会恢复可再次点击；失败时会**自动展开「手动填起点」**。

- 距离全部在本机计算，**不引入地图 SDK、不调第三方 API**；「打开平台 / 导航」仍是你主动点击的外链。
- 店铺坐标是记录的可选字段（`lat` / `lng`），旧数据不填也完全兼容，不需要迁移。

## 店铺定位：高德 POI 搜索 + 地图选点

记一餐的「完整记录」表单里新增了三个**互相独立**的定位入口，任一可用即可完成定位，不把记录流程绑死在搜索上：

| 入口 | 依赖 | 结果 |
| --- | --- | --- |
| 高德搜索 | 网页版：主页面 JS API 插件；APK：内嵌地图页里的同一套插件 | 候选列表 → 点「用这家」才回填店名 / 城市 / 商圈 / 地址 / 经纬度 |
| 地图选点 | 高德 JS API 底图 | 点图放临时标记 → 「确认使用此位置」才写入；取消不改动原坐标 |
| 手填经纬度 / 用当前位置 | 无 / 定位权限 | 始终可用，写入后来源记为「手动」或「当前定位」 |

- **双路径、同一套交互**：网页版仍在主页面按需加载 `PlaceSearch` / `AutoComplete`；APK 内因主页面源 `https://localhost` 不在 Key 域名白名单，改为把关键词经既有 `fz:poi-search` postMessage 发给内嵌地图页（源 `violetz10032.github.io`），由内嵌页执行 `AMap.PlaceSearch` 后回传精简结果。宿主只发关键词与城市，只接收店名、地址、类型、城市/区域、经纬度；**不回传店铺备注、消费金额等记录隐私字段**。两端共用同一个候选列表、同样的 400ms 输入防抖、同样的「用这家」确认与错误码文案。
- **必须显式确认**：搜索候选只展示，不自动选第一条、不自动写字段；点「用这家」才回填。
- **失败给真码**：`INVALID_USER_DOMAIN(10006)`、`INVALID_USER_SCODE`、`USERKEY_PLAT_NOMATCH`、`INVALID_USER_KEY`、`DAILY_QUERY_OVER_LIMIT`、`OVER_QUERY_LIMIT` 原样显示并附处理建议；`no_data` / `timeout` 单独区分，不吞成一句「搜索失败」。
- **距离自动带出**：回填坐标后，若「起点」已设经纬度，按 Haversine 实算直线距离写入「与我距离 km」，并标注「已按起点实算，可手改」；你手填过的距离不会被覆盖。
- **坐标来源**：店铺级定位写入 `fandazi.shopmeta` 条目的可选 `location`（`coordinateSystem:'GCJ02'`、`source`、`amapPoiId`、`formattedAddress`、`cityCode`、`verified`），记录里新增可选 `locationSource`。旧数据没有这两个字段时按空读取，不迁移、不改键名。
- **同一家店**：定位元数据按现有 `shopIdOf(店名, 城市)` 归并，与平台链接 / 补充字段同一套店铺档案，不重复建档。
- **已知限制（与地图同源）**：搜索与底图共用同一 Key 与同一套域名校验。网页版直接加载；APK 内经内嵌地图页执行（`fz:poi-search` / `fz:poi-result`），内嵌页为搜索按需**隐藏挂载**，不改变地图页当前可见状态。若内嵌页不可达或 8 秒未就绪、搜索 10 秒无响应，会明确提示原因并保留手填经纬度与「用当前位置」两条退路，不假装搜到；高德返回的 `INVALID_USER_KEY` / `DAILY_QUERY_OVER_LIMIT` 等真码原样透出。协议版本 `FZ_PROTO=4`，缓存里的旧内嵌页会因缺 `fz:poi-search` 而超时提示，重新部署 Pages 后即恢复。地图选点失败同样保留手填与「用当前位置」。
- **测试**：`.tmp/poi-pick-test.js` **17/17 通过**（网页端 mock AMap）；`.tmp/poi-embed-test.js` **18/18 通过**（真实 `map-embed.html` + iframe 内 AMap 桩）：请求→内嵌页→回包→回填全链路、字段隐私白名单、输入防抖、错误码、搜索超时、内嵌页不可达回落手填、控制台无错误、375 宽无溢出。

## 视觉与图标

界面按「约饭 / 记录美食」的场景设计，而不是通用工具箱：场景感来自碗、筷子、热气、餐桌，而不是堆装饰。

### 设计原则

- **不重排骨架**：四视图（列表 / 日历 / 日记 / 地图）、底部四标签、三套皮肤、明暗主题全部保留；视觉改动只发生在 CSS 变量层与样式覆盖，少量包裹元素（如按钮内联图标）不改布局结构。
- **主次分明**：列表条目按「店名 → 城市/商圈 → 人均 / 综合评分 / 菜系」排出视觉权重，日期、餐次、人数等辅助信息退到第二层；主按钮实心 44px 起，次按钮描边/浅底，危险操作单独用红系。
- **桌面感**：卡片圆角与阴影跟随皮肤的 `--r` 自适应（默认 18px；P5 皮肤仍是 2px 硬边 + 偏移阴影），不写死像素，因此三套皮肤 × 明暗六种组合都不会出现白底/黑底残留。
- **克制动效**：页面切换与卡片出现 140–180ms，`cubic-bezier(.2,.7,.2,1)`，不做弹跳、不做视差；系统开启「减少动态效果」时全部动画降到 0.001ms。
- **点击目标**：主按钮 ≥44px（`.btn-primary` / `.btn-block`），图标按钮视觉 34px、用 `::after` 扩大到 44px 命中区，底部标签 56px。

### 图标规范

- **全部自绘内联 SVG**，不引入任何图标字体、外部图片或 CDN：24×24 网格、1.6px 描边（小尺寸 14px 图标用 2px 保证清晰）、圆头端点、圆角矩形统一 R6。
- 统一入口：样式类 `.ico`、`.ico-14`、`.ico-16`、`.ico-20`；JS 侧图标由 `ICON`（A 套）/ `ICON_B`（B 套）常量生成，静态标记只写 `data-ico` 名，启动与切换时统一水合。
- **两套应用内图标可切换**：「我的 → 图标风格」选 A 定位碗（线性细描边，默认）或 B 城市一碗（实心 / 粗线）。切换即时重绘全部已渲染图标，写入 `fandazi.iconStyle`（`a` / `b`），刷新后保持，并纳入完整备份（`备份 → 完整备份` 的 `localConfig`；普通 JSON 导出只含记录，不含本机偏好）。与明暗主题、P3/P4/P5 皮肤正交，只换图形不改色板与布局。
- 状态图标（关闭、上/下月、地图缩放）、标签栏、记录卡操作图标都走同一套映射，因此切换后不会出现「一半线一半面」。
- 空状态统一使用一枚轻量碗筷插画（CSS `mask-image` 内联 SVG），颜色取自 `--accent-text`，在明暗与三套皮肤下自动跟随（该插画不随 A/B 图标风格切换）。

### App 图标（桌面 / PWA）

| 方案 | 资产位置 | 现状 |
| --- | --- | --- |
| **A 定位碗**（默认） | `icons/`（7 个 PNG）+ `android-app/.../mipmap-{mdpi..xxxhdpi}/`（各密度 `ic_launcher` / `ic_launcher_round` / `ic_launcher_foreground` / `ic_launcher_background`）+ `mipmap-anydpi-v26/` 自适应 XML | 正在使用；PWA 与 APK 的启动图标都固定为它 |
| **B 城市一碗**（可选） | `docs/icon-candidates/b/`：`icons/` 全套 7 个 PNG + 五档 `mipmap-*` 同四件套 + `mipmap-anydpi-v26/` 自适应 XML | 完整备用资产，可在仓库内替换；**桌面图标暂不随应用内开关切换**（PWA 无此能力，Android 需 activity-alias，尚未启用） |

两套都是「一碗」语义：A 用品牌橙渐变底 + 奶油白碗 / 筷 / 定位针；B 用奶油底 + 城市天际线 + 深橙碗。PWA `manifest.webmanifest` 固定引用 `icons/icon-192.png` 等 A 套，**系统层面无法在应用内切换启动图标**；应用内「图标风格」只影响导航栏、按钮、空状态等界面图标。

**换桌面图标只需把 `docs/icon-candidates/b/icons/` 与 `mipmap-*`、`mipmap-anydpi-v26/` 覆盖到对应位置并递增 `sw.js` 里的 `VERSION`**（当前 `fandazi-pwa-v8-20261106`），manifest / AndroidManifest 的引用路径不变。重新生成图标的脚本在 `.tmp/gen-launcher-icons.js`（用本机 Chrome 光栅化 SVG，不提交到仓库）。

## 返回层级（浏览器返回 / Android 返回键 / 侧滑返回）

移动端返回**不再直接退出应用**，而是按「由内到外」逐层回退，只有最外层才允许退出：

1. **弹层 / 覆盖层**：记录表单、各类详情、备份面板、投票、教程、新手引导、外观设置、清理确认等共 23 个遮罩层，返回 = 关闭最上层那一个；同一时刻叠了多层（例如引导叠在导出面板上）时按「后开先关」逐层关闭。
2. **子视图**：记录页的日历 / 日记 / 地图 → 回到列表；推荐页的聚餐 / 健身 / 好友 → 回到今日推荐。
3. **最外层**：列表 + 无弹层时才允许退出（Android 上继续按返回会退出应用；浏览器里由浏览器接管）。

实现方式（`index.html` 里「返回层级」代码块）：

- **不新增存储键**，返回栈只存在于内存 + `history`。进入弹层或子视图时 `history.pushState({fzBack:1})` 压一道守卫；退回最外层时用 `history.back()` 消耗掉它，因此普通刷新/关闭不会残留历史。
- 弹层是靠给遮罩加/删 `.hidden` 打开的，`showView()` / `showPanel()` 覆盖不到，所以额外用一个 `MutationObserver` 监听 class 变化后调用 `syncBackGuard()`，统一维护守卫数量（最多一道，不会随开合次数累积）。
- 关闭动作复用各弹层已有的关闭函数（`MASK_CLOSERS` 表），所以「点遮罩关闭」「✕ 按钮」「ESC 关闭引导/教程」的行为与以前完全一致；弹层内未保存内容的提示也沿用弹层自身的既有策略，没有新增强制确认。
- **APK / Capacitor**：代码会探测 `window.Capacitor.Plugins.App.addListener('backButton')`，存在时接管系统返回键（无可回退层级才 `exitApp()`）。APK（v1.0.2）已装 `@capacitor/app` 并接了原生返回事件（400 ms 防双触发）；网页版 / PWA 继续走 history 分支，二者不会同时执行两次。真机手感仍待验证。

## 记录体验 2.0（P0：快速记录 / 选店 / 预填）

本段只做「记录」的入口与最短路径；照片管理见下一节，连续记录与历史修改见「记录体验 2.0 · 第二段」，语音仍留给后续探明。

### 三种入口

| 入口 | 位置 | 预填 | 保存要求 |
| --- | --- | --- | --- |
| 快速记录 | 顶部「+ 记一餐」/ 列表页 | 日期=今天，时段按当前时间给**建议**，人数=默认人数 | 只要求店名（日期自动带今天），金额 / 评分 / 照片全选填 |
| 完整记录 | 表单内「完整记录」分段 | 同上 | 新建时仍要求人均或总价；编辑已有记录不强制 |
| 补录历史 | 表单内「补录历史」分段 | 日期**先清空**，必须手选实际到访日 | 金额可空 |

「吃完顺手记」：列表页顶部独立轻入口，直接进入 `snap` 模式，只显示选店、店名、备注、照片；日期 / 金额 / 时段 / 人数 / 城市等字段隐藏但保留值（日期=今天），避免为了记一顿饭先滑三屏。

### 餐厅快捷选择（只用于新建；编辑时不显示，防止改挂别的店）

- 四个标签：最近记录（最近到访 5 家）、常去（按到访次数）、收藏（独立收藏夹，与想去清单分开）、最近搜索（保存过、最多 6 条）。
- 搜索匹配店名 / 商圈 / 城市 / 菜系：繁体转简体、全角转半角、去尾部括注与「店 / 餐厅」等后缀；前缀命中优先，其次到访次数。
- 选店只**补空字段**：店名、城市、商圈、地址、品类、坐标、距离；人数取这家店上次的人数；**不会**自动填金额、评分、评价。
- 别名归一后命中已有店时，保存阶段也会归到同一档案，不新建重复店铺；城市或地址冲突时不合并。
- 搜索无匹配时出现「+ 新建『xx』」，点一下即填入店名，保存时首次建档，不用退出页面。

### 预填与记忆

- 选店后显示该店档案：到访次数、上次日期、上次人均 / 评分 / 人数、上次评价、常用标签（点一下加入本次标签）。
- 历史人均标注为「仅作参考，不会自动填成本次金额」，避免把总价或实付算错。
- 时段按当前小时给出建议（早 / 午 / 下午茶 / 晚 / 夜宵），只是建议，可改；补录模式下不自动改时段提示。
- 保存后记住上次人数、场景与打开模式（可在「我的 → 记录默认」关闭）；「记录默认」可设默认人数 / 默认场景 / 默认模式（快速 / 完整）。

### 快速保存与后续完善

- 轻量形态（快速 / 补录 / 顺手记）的「保存」是**吸底栏**：`position: sticky; bottom: 0`，随弹层滚动始终贴在底部，点完店不用下滑就能保存；完整模式仍用表单末尾原有的保存 / 取消，按钮位置未动。
- 吸底栏参与文档流而不是 `fixed`：滚到表单底部时它停在内容之后，不会永久压住最后一行；弹层底部的安全区留白沿用原 `.sheet` 的 `calc(22px + env(safe-area-inset-bottom))`。
- 键盘弹出时弹层按 `visualViewport` 收缩（既有 `fitSheetToViewport`），吸底栏跟着贴到收缩后的底部；关闭表单 / 返回时弹层隐藏，吸底栏随之消失，没有新增 history 守卫。
- 非「完整记录」模式保存后**不关闭表单**，页内出现成功块：「未填：金额 / 照片 / 评分；这些会保持为空或『未评价』，不会生成虚假评分。」并给出「再记一家（连续记录）」「继续完善」「完成，返回首页」；此时吸底栏自动收起，避免重复提交。
- 同一表单再次提交 = 更新刚才那条（`editingId` 已就位），不会重复入库。
- 「继续完善」切到完整记录并聚焦金额；此时只补评分 / 备注也能保存（编辑已有记录不强制金额）。

### 数据与兼容

- **没有新增存储键**：`defaultPeople / defaultScene / defaultMode / rememberDefaults / recentQueries` 都写进既有 `settings`，v1 与已迁移的 v2 都经 `migrate` 白名单归一化（缺省值分别为 4 / 空 / quick / 开 / 空数组）。
- v1 直接写 `fandazi.v1`；v2 只写 `fandazi.v2` 并重建 shops / visits，**不双写 v1**（实测保存前后 `fandazi.v1` 逐字节一致）。

## 记录体验 2.0 · 语音输入（方案 1：网页 / PWA 在线识别）

只做**网页 / PWA 在线语音**：使用浏览器内置 Web Speech（`SpeechRecognition` / `webkitSpeechRecognition`），**不装原生插件、不申请 `RECORD_AUDIO`**，APK 壳没有新增任何录音权限。

### 入口与可用性

- 入口在记录表单「店名」与「备注」标题右侧，按钮文案「语音」，麦克风线性图标；视觉高度 32px，伪元素把命中区扩到 44px。
- **先探测再显示**：`window.SpeechRecognition || window.webkitSpeechRecognition` 不存在，或当前页面不是安全上下文（非 HTTPS / 非 localhost）时，两个入口保持隐藏，**不留点了没反应的死按钮**。
- 支持时识别语言固定 `zh-CN`；识别结果只写进当前输入框，**可直接修改，不会自动保存**，也不会随记录上传。

### 首次使用必须明确同意

- 第一次点「语音」弹出应用内确认层，逐条说明：音频会**上传到云端语音服务**识别、结果只写进本次表单输入框、不会自动保存。
- 同意复选框**默认不勾选**，「同意并开始」按钮默认禁用；只有用户主动勾选后按钮才可用。点「不同意，改用手输」不会启动识别，并提示已改用手输。
- 同意后记在本机 `fandazi.voiceConsent=1`，同一设备后续点语音直接开始，不再重复弹窗；不想上传时仍可随时改用键盘输入。

### 识别体验

- `continuous + interimResults`：临时结果实时写进输入框，最终结果确认后落定；`continuous` 在 Chrome 上不稳定，统一用 `onend` 自动重启补丁（间隔 240ms），把一次说话被切成多段的情况接回同一段文本，不丢字。
- 单次会话上限 60 秒、最多自动重启 20 次；连续 3 次静音无内容则主动结束。
- 识别中按钮变为「聆听中…」并带呼吸态；再次点击即结束，已识别内容保留在输入框。
- 识别过程中用户开始键盘输入，视为明确改用手输：立即结束识别，保留手打内容，不覆盖。
- 输入框长度按原字段限制截断（店名 40 字、备注 300 字）。

### 已知限制（语音）

- 网页端需要 **HTTPS（或 localhost）+ 麦克风授权**；`http://` 局域网 IP 下入口会隐藏。
- 识别依赖浏览器内置在线语音服务（Chrome / Edge 可用；Safari、多数 Android WebView 不提供），**APK 内通常探测不到能力，入口会隐藏**，不影响手输。
- 识别时音频会离开设备交给云端语音服务，这是本功能唯一的外传数据；不识别时不上传任何内容。
- 真机麦克风、弱网、方言口音的识别质量**未真机验证**；本轮全部为 headless Chrome + mock 行为验证。

## 跨设备同步 MVP（加密私有 Gist）

两台设备用**同一个同步口令**，通过你自己的**私有 GitHub Gist** 传递到店记录与照片：记录放主 Gist，照片放**另一个独立 Gist**。两者都在浏览器内加密后才上传，服务端只看到密文。GitHub 为**境外服务**，开启前必须先在弹层里明确勾选同意。Gist 通道**明确不可用**（不可达 / 超时 / 5xx / 限流）时，会自动切到你自己的**私有仓库 Contents API**，切换原因写在设置卡里，恢复后自动切回。

### 怎么用

1. **设备 A**：打开「我的 → 跨设备同步」→ 点 **开启同步** → 粘贴 Token、设置口令（≥10 位，二次确认）、勾选同意 → **创建并上传**。
2. 成功后卡片显示 **Gist ID**，点「复制」记下来（另一台设备要用它加入）。
3. **设备 B**：同一个面板点 **加入已有空间** → 填 A 显示的 Gist ID、同一个 Token、同一个口令 → **加入并合并**。
4. 之后任意设备改完记录，点 **立即同步**（刷新后需要重新输入口令，因为口令不落盘）；另一端再点一次即可拿到改动。

### Token 从哪来

- 需要在 GitHub 上至少有 **`gist`** 权限（输入框旁有同样提示）。若之后触发 Contents API 回退，还需要 **`repo`** 权限：回退时会自动在你的账号下创建私有仓库 `fandazi-sync`（已存在则直接用），Token 缺 `repo` 权限时不会假装切换，而是退回 Gist 通道并提示重新生成 Token。
- 已安装 `gh` CLI 的机器可以直接：`gh auth token`。拿到的 `gho_` 类型 Token **可直接作为 Bearer 凭据**调用 Gist API（实测正常），且**不会自行过期**。
- 撤销路径：GitHub → Settings → Applications → **Authorized OAuth Apps** → GitHub CLI → Revoke。
- Token 只存在本机 `localStorage` 的 `fandazi.sync.token`，**不写进记录库、不参与导出**；点「断开」会清除 Token 与 Gist ID（远端密文不会被删）。

### 加密与合并规则

| 项 | 实现 |
| --- | --- |
| 密钥派生 | PBKDF2-SHA256，**600,000 次迭代**，16 字节随机 salt |
| 加密 | AES-256-GCM（12 字节 IV、128 位 tag），AAD 绑定分片序号 / 总数 / 明文 SHA-256 |
| 分片 | 明文 gzip 后按 **512 KB** 切分，最多 **12** 片；每片单独加密成一个 Gist 文件 |
| 口令 | **绝不落盘**；派生密钥只存在内存，刷新页面即失效 |
| 回读校验 | 上传后重新 GET，校验 `writerId` + `payloadRev`，不一致就判定并发冲突并中止 |
| 合并 | 记录级 LWW（按 `updatedAt`）；`baseHashes` 判断「仅本机改 / 仅远端改 / 双方都改」 |
| 冲突 | 双方都改时**较新版本胜出，旧版本保留为副本**（`id = cf_<原 id>_<哈希前 8 位>`、`conflictOf`、`source:'conflict'`、备注前缀 `[冲突副本]`），从不静默丢弃 |
| 冲突副本可复现 | 副本 id 取自被覆盖版本的内容哈希，`updatedAt` 也继承被覆盖版本的时间；两台设备各自生成的副本逐字段相同，后续同步不会把副本再复制一层 |
| 同时新增 | 两条不同记录直接取并集，双方都保留，不产生副本 |
| 删除 | 墓碑 `{entity:'record', id, deletedAt}`，跨设备传播删除；**墓碑保留 180 天**，超期在下一次同步时自动清理 |
| 删除 vs 修改 | **删除优先**（不复活）；另一方在删除后做过的修改仍会保留成一条 `[冲突副本]`（`conflictFrom:'delete-edit'`），不静默丢弃 |
| 失败保护 | 合并前自动建 `before-sync` 恢复点；任何一步失败都**不改动本机记录**，可在「备份与恢复」里回滚 |
| 并发 | 本机 60 秒同步锁，避免同设备两个任务互相覆盖 |

### 照片同步（最小版）

- 记录里不再内嵌照片数据，只携带 `photoRef` 列表：**内容 SHA-256 去重 + 主口令派生的 HMAC 不透明引用**（`ph_` + 32 位十六进制），远端看不到文件名、店名或照片内容。
- 照片本体存**第二个私有 Gist**：容器 JSON（全图 + 缩略图 + 尺寸）加密后按 **512 KB 明文分片**，每个 Gist 文件 ≤1 MB；manifest 单独一个文件，记录照片引用与分片校验信息。
- 拉取成功即写入本机 IndexedDB（`id` 就是 `photoRef`），记录列表/详情可直接显示缩略图与原图。
- **照片失败不阻塞主数据**：拉取失败、超配额、照片 Gist 丢失都只标记缺口，主记录同步照常成功；设置卡显示「本机缺 N 张照片」并提供 **补齐照片**（重新走一次同步，失败会再次提示）。
- 单轮最多上传/下载 8 张、总预算 16 MB，超出部分留到下一轮手动同步，不做复杂退避。
- IndexedDB 仍为原结构（版本 2），仅在照片记录上增加可选的 `ref` / `sha` 字段；回退旧版代码不会触发 VersionError。
- **引用归零回收**：每轮同步按「当前所有记录的 `photoRef`」重算引用；某张远端照片连续 **7 天**无人引用才删除远端文件与 manifest 项（重新被引用则清空计时）。只回收远端，不动本机照片。
- 回收与墓碑清理都在**下一次同步**执行，失败不影响主记录；设置卡会显示「已回收 N 张无引用照片」。

### 失败重试（outbox）

- **失败项不丢弃**：`dirty`、未同步墓碑与 `baseHashes` 缺口本来就落在 `localStorage`，outbox 只额外记录排队状态（第几次、下次时间、最后错误、是否标死）。
- **可重试**（网络中断、超时、5xx、403 限流 `E_RATE`、并发冲突）：按 **30 秒 → 2 分钟 → 10 分钟 → 1 小时** 指数退避，之后封顶 1 小时；成功一次即清零。
- **不可重试**（401 Token 失效、403 权限不足、422 校验失败、404 空间不存在、口令错、公开 Gist、超上限）：**直接标死**，不再无意义地重试，并在设置卡给出可操作提示（如「重新粘贴 Token（需 gist 权限）」「核对同步口令与 Gist ID」）。
- **自动处理时机**：网络恢复（`online`）、回到前台（`visibilitychange` / Capacitor `appStateChange`）、打开应用，以及每次编辑后 5 秒防抖，都会把待同步队列重排一次并在后台依次处理；口令只在内存里，刷新后无口令时队列保留，界面提示「输入同步口令后自动重试」，点按钮会先弹出口令输入。
- **界面**：设置卡显示「待同步 N 条 · 第 k 次重试在 hh:mm（约 X 后）」，并可展开明细；标死时显示「同步已暂停：<原因（可操作提示）>」与 **重新尝试** 按钮。失败项始终计入「待同步 N 条」，不会被静默清零。

### 通道回退（Gist → 私有仓库 Contents API）

- **触发口径**：只有 Gist 通道**明确失败**才切——不可达、超时、5xx、403 限流。401 Token 失效、403 权限不足、422 校验失败、404 空间不存在属于账号/空间问题，**不回退**，避免把账号问题误判成通道故障。
- **不静默双写**：任一时刻只写一条通道。回退前不会把同一份数据再往 Gist 写一遍；Gist 没成功时也不会显示「远端已更新」。只有写入并**回读校验**通过才更新 `lastRev` / `lastSyncAt`。
- **两通道互认**：两条通道使用**同一份加密 manifest 与 payload**（同 format / version / salt / 分片校验），只是存放位置不同。回退后仍按已有 `rev` / `updatedAt` 合并逻辑处理，不强推、不覆盖；Gist 恢复后切回时，Contents 期间产生的记录会随下一轮同步补回 Gist。
- **Contents 写入**：每个文件 PUT 都带上一轮读到的 **`sha`** 做乐观锁；`sha` 过期返回 409 / 422 时按并发冲突处理（`E_CONFLICT`），重新读取合并后再写。由于 Contents 的 PUT 不是原子操作，分片按轮次命名（`data-r<rev>-*.fz.json`）先写、manifest 最后写：manifest 冲突时旧的 manifest + 旧分片仍完整可读，不会把远端写成无法解密的半成品；manifest 写成功后才清理旧分片。
- **可见性**：设置卡显示**当前通道**（Gist / 私有仓库 Contents API + 仓库名）与**上次切换时间、原因、错误码**；Contents 通道下提供 **「重试 Gist 通道」** 手动切回，另外每 10 分钟自动探测一次，恢复即切回。
- **仓库初始化**：首次回退时若未配置仓库，会自动创建私有仓库 `fandazi-sync`（`private: true`）并写入加密文件；目录默认 `fandazi-sync/`。Token 只有 `gist` 权限时回退失败并如实提示，不会留下「已切换」的错觉。

### 本版未包含（最小版明确不做）

- 增量/断点续传之外的性能优化（大图库批量同步仍按每轮 8 张推进）
- 多设备并发压力测试

| 场景 | 最终状态 | 冲突副本 |
| --- | --- | --- |
| 同时改同一家店（A 改 `updatedAt` 早于 B） | 两台都只剩 B 版本 | 两台各有 1 条同 id 的 `cf_r1_*`，备注 `[冲突副本] A 改`，`updatedAt` 等于 A 的原时间 |
| 连压 3 轮后 | 记录数 3、副本 1，双方 id 完全一致 | 不重复复制 |
| 同时新增（A 加 r3 / B 加 r4） | 两台都有 r3、r4，记录数 5 | 不新增副本 |
| 一边删一边改（A 删 r2 / B 改 r2） | r2 在两台都不再出现，墓碑 1 条 | 两台各有 1 条同 id 的 `cf_r2_*`，内容为 B 的修改 |
| 删除后再压 2 轮 | r2 不复活、记录数 5、副本总数 2，双方 id 一致 | 不增殖 |

压测暴露并修复了两个真问题：① 同一冲突在两台设备各自生成的副本 `updatedAt` 毫秒差不同，下一轮被当成新改动又复制一层（副本套副本）；② 一边删一边改时修改被删除规则静默吞掉。修法是让副本内容可复现（`updatedAt` 继承 loser），并把删除后仍被修改的版本保留成 `conflictFrom:'delete-edit'` 的副本，未放宽任何断言。

### 已知限制（同步）

- 同步的是**到店记录与照片**；想去清单、**收藏**、地点、设置、投票与**在家吃数据**（`fandazi.recipes` / `fandazi.homefb` / `fandazi.pantry` / `fandazi.cooklog` / `fandazi.homeweek` / `fandazi.cookprog`）仍不同步。
- 照片每轮最多 8 张 / 16 MB，图库很大时需要多点几次「补齐照片」；缺图只是标记，不影响记录。
- 删除记录不会回收远端照片（最小版不含引用计数回收）。
- 口令忘记只能换新口令重新建立空间，**旧密文无法解密**。
- 主通道是 Gist；企业网络屏蔽 `api.github.com` 时会提示网络异常，本机数据不受影响。Contents API 回退同样依赖 `api.github.com`，只是换到私有仓库，**不能绕过对 GitHub 的整体封禁**。
- 回退到 Contents API 需要 Token 具备 `repo` 权限；首次回退会自动创建私有仓库 `fandazi-sync`，介意自动建库可先手动建好同名仓库。
- Contents 通道下每轮同步会写 manifest + 全部分片（单文件 PUT，不是单次原子提交）；冲突时旧版本保持可读、下一轮重试合并，极端并发下可能出现一次额外的重试。
- 后台重试需要口令在内存中（即本次打开应用后至少同步过一次）；刷新后要先输入口令，队列才会继续。
- 同步是**手动触发 / 打开同步弹层触发**的，没有实时推送；两台设备并发改动要靠下一轮同步收敛，收敛前各自看到的都是自己那一版。
- 删除不可撤销：墓碑优先于修改传播（改动只以冲突副本留档），墓碑保留 180 天后不再参与合并，届时各设备只是不再收到这条删除信息。
- 冲突副本的 `updatedAt` 继承被覆盖版本的时间（为了两台设备生成同一份副本），因此它在列表里显示的是那次改动的时间，而不是发现冲突的时间。

## 照片（P1：店铺 / 到店 / 菜品）

### 三类照片分开

- 记录表单里的照片分三组：**店铺照片**（门头、菜单、环境）、**到店照片**（小票、桌面、排队）、**菜品照片**。每组独立添加、独立设封面。
- 每组都支持**相机 / 相册**（`accept="image/*"`，`multiple` 多选）；照片只存在本机 IndexedDB，不随任何导出/分享上传。
- 同一张照片只属于一个分类；组内可排序，**第一张即封面**（列表卡片优先显示封面）。

### 添加、预览、编辑

- 添加后立即在表单内显示缩略图；点击缩略图打开大图预览层（`#photoViewMask`，参与返回层级，返回键 / ✕ / 点遮罩都能关）。
- 预览层支持：上一张 / 下一张、看原图（1:1 不缩放，可拖动查看）、设为封面、左移 / 右移、替换、删除。
- **批量模式**：点「批量」进入多选，勾选后可一次删除；退出批量前不会执行删除。
- 表单里删除照片是**延迟生效**的：点 ✕ 只从本次表单移除，取消表单不会丢图；只有点「保存」才真正清理无引用的照片。

### 压缩与加载策略

- 照片入库前用 canvas 双档压缩：原图 ≤1280px、JPEG q≈0.72；缩略图 ≤240px、q≈0.6。列表/表单优先读缩略图，只有打开预览「看原图」才读全图，避免一次性解码全部原图。
- `photoGetThumb()` 优先返回 `thumb`，旧数据没有缩略图时回退全图；`hydratePhotos()` 按 `data-thumb="1"` 懒加载。

### 删除、引用与孤儿

- 记录里的照片以 `photos: [{ id, cat }]` 存储，同时保留 `photoIds` 与旧字段 `photoId`（兼容旧记录 / 旧导出）。
- 删除记录时**按引用计数**清理：同一张照片若仍被其它记录引用，不会被误删；只有没有任何记录引用时才从 IndexedDB 删除。
- **孤儿照片只报告、不自动删**：「我的 → 诊断」里显示「孤儿照片 N 张（有文件、无记录引用）· 只报告不自动删除」。
- `migrate()` 会把 `photos / photoIds / photoId` 一起归一化保留（此前只保留 `photoId`，会导致重载后多图丢失，已修）。

### 与 v2 的映射

- v2 的 `visitOfRecord` 会写 `photos / photoIds`，`recordFromVisit` 会还原 `photos / photoIds / photoId`；`V2_MAPPED_KEYS` 已包含这些字段，v2 读写不会丢分类信息。

### 未真机验证

- Android 真机上的相机/相册选择器、WebView 内大图预览的内存表现、系统分享面板（照片不进分享）**未真机验证**；本轮验证均在 375×812 headless Chrome 完成。
- 本轮实测（新脚手架：固定 profile + 单实例 + 禁用扩展）：P1 **21/21**；回归：返回层级 **44/44**、P0 **28/28**。
- 交互扫描（`node .tmp/dead-btn-test.js`，可复跑）：20 个视图 / 弹层场景、共 **205** 个可点击元素，逐个真实点击并比对「监听是否触发 + 视图 / 弹层 / toast / localStorage / 画布像素」是否变化。修前发现 **1 个静默无响应**：对已加入「不再推荐」的店再点按钮，`blackStore` 直接 `return`（现在补了提示）；修后异常 **0**。外链跳转、文件选择、系统分享、浏览器安装提示属外部副作用，单列为 SIDE，不计死按钮。
- 触控命中：图标按钮视觉 34px / 命中 44px；地图工具条改为视觉 40px、命中 44px、间距 8px（原来 30px+5px 展开会与相邻按钮叠压、点错或没反应）；分段器 / 筛选 chip / 标签 chip 增加按压态（`scale(.98)` + `brightness(.96)`），并统一 `touch-action:manipulation` 去掉移动端 300ms 点击延迟；照片角标删除按钮 22→28px。

## 平台链接与补充信息（信息来源标记）

给一家店保存大众点评 / 美团 / 小红书 / 高德 / 抖音等页面地址，顺手记电话、参考人均、排队情况；入口不新增并列页签，直接挂在现有「想去清单」和「地图 → 店铺详情」里。

- **只保存链接，不探测**：点「链接 / 补充」→ 粘贴地址 → 保存；点标题在新窗口打开原页面（`target="_blank"` + `rel="noopener noreferrer"`）。应用不做可达性探测、不抓取页面、不模拟登录。
- **状态由用户标记**：每条链接可标「正常 / 待确认 / 无法访问」，切换时记录「状态更新时间」；应用不会自行判断链接是否失效。
- **一店多链**：同一平台可保存多条（例如总店与分店），每店最多 20 条；完全相同的 URL 会被拒绝，重复保存不会产生副本。
- **来源与时间**：补充字段（电话、参考人均、平台评分、排队 / 等位、营业状态）只作参考，统一显示「用户填写 · 日期」；没填就是「暂无数据」，不推测、不补全。
- **不污染事实数据**：参考人均、平台评分**不会**写入到店记录的实际消费金额、个人评分或统计；到店与否仍只由用户主动记录。
- **存储**：独立增量键 `fandazi.shopmeta`（按 `城市 + 店名` 的稳定 id 归档），**不写进 `fandazi.v2.shops`**，避免被 v2 每次保存时的重建覆盖；记录里的坐标 / 金额 / 评分仍是唯一事实来源。
- **覆盖范围**：完整备份包含该段（见下）；好友分享包与跨设备同步**尚未包含**平台链接与补充信息（同步只覆盖到店记录与照片），换机或分享时这部分按「未同步」处理。

实测（375×812 headless Chrome）：平台链接与首用引导 **16/16** 通过——空列表三条入口（含导入弹层）、空态引导、URL 补全、同平台多条、重复拒绝、状态标记与更新时间、字段来源与不污染金额、编辑 / 删除、刷新持久化、备份 v5 往返、旧备份缺失该段保持现状、地图店铺详情与想去清单两个入口、链接新窗口安全属性、全程无控制台错误。

## 店铺档案与到店记录一体化（第一阶段）

在**现有店铺档案**（地图 → 店铺详情 sheet）上做增强，不新建店铺表、不复制第二套店铺数据。所有新能力只读写两处已有数据：`db.records`（v2 模式下投影自 `fandazi.v2.visits/shops`）与 `fandazi.shopmeta`。

- **又来了**：档案页第一个按钮，复用现有 `quickEat()` 打卡流程（默认时段、金额可空、保存后记录 +1），不新增旁路记录、不改写原有表单逻辑。
- **重复店铺识别**：按以下优先级给出候选，**从不自动合并**：
  - `poi`：两边 `shopmeta.location.amapPoiId` 相同（最高优先）；
  - `addr`：店名归一化相同 + 城市相同（「上海 / 上海市」视为同城）+ 地址一致或互相包含；
  - `coord`：店名与城市相同 + 两边坐标相距 ≤ 200 米；
  - `name`：店名与城市相同但缺坐标 / 地址，标记「需人工确认」。
  候选卡片提供三个明确动作：**合并预览**、**标记同一家（不合并）**、**不是同一家**；地图工具条另有「重复店铺扫描」入口，一次扫描全库并只列出候选，**绝不自动合并、绝不自动删除**。
- **合并前并排预览**：弹出预览 sheet，左右两栏列出双方城市 / 区域、地址、坐标、到店条数 / 评分 / 人均、照片数、收藏与想去、旅行引用、推荐反馈（含历史条数）、黑名单、标签、平台链接与补充字段；选择「保留源店资料」或「保留目标店资料」（默认后者）后才写入。
- **合并迁移清单**：到店记录只改 `name` / `city`（记录 id、日期、评分、金额、菜品、标签与照片全部保留，照片挂记录所以自动跟随）；收藏、想去、推荐反馈（含 `history`）、黑名单、旅行 stop（`shopId` 显式迁移，重复 stop 合并状态 / 日期 / 备注）、`shopmeta` 平台链接 / 补充字段 / 别名一起迁到目标店，目标已有则去重。迁移后逐项校验源键 / 源 `shopId` 不再存在，**不留悬空引用**。
- **撤销合并**：成功合并后把迁移前后 5 个键（`db` / `shopmeta` / `trips` / `favorites` / `feedback`）的原始快照写入 `fandazi.mergeundo`，弹层提供「撤销这次合并」。撤销前逐键比对当前数据与合并后的快照：任何键被再改动过就**拒绝覆盖并明确提示「已保留现状」**，不静默覆盖；撤销成功则 5 个键逐字节还原，并删除撤销快照。快照写入失败（本机空间不足）时合并仍完成，但界面会明说「本次合并无法撤销」。
- **合并失败回滚**：记录写入失败、补充信息写入失败、收藏或旅行 stop 迁移失败，均按快照整体回滚到合并前状态，并给出用户可见的中文原因，不只写日志。
- **到店时间轴**：按到访日期倒序展示历次到店（日期、评分、人数、实际 / 参考人均、照片数）；点击某一行复用现有记录详情，不另写渲染逻辑。
- **人均与评分变化**：三格统计 + 首末变化 + 逐次样本。
  - **实际人均** = 该次实付总额 ÷ 人数，仅对通过现有 `recordCountsInStats()` 且金额、人数都有效的记录计入；
  - **参考人均** = 记录里手填的 `perPrice`，缺失就是缺失；
  - 两类数值分开显示、分开求平均，**互不顶替**；没有数据时显示「暂无数据」，不估算、不用参考值填充。
- **三类反馈严格分离**：
  - **想去**：只写 `db.wishlist`（`wishAddStore()`），提示「已加入想去清单（不算到店）」；
  - **推荐反馈**：写 `fandazi.feedback`，带 `surface` 标明来源（每日推荐 / 抽签 / 盲盒 / 朋友推荐 / 聚会推荐 / 健身推荐 / 旅行推荐），只影响推荐排序；
  - **真实到店**：只有 `quickEat()` / 记录表单保存才写 `db.records`。

## 旅行计划

把「想去清单」或已有记录的店按天数排进行程，出发前用「记一餐 / 确认到店」把安排带到真实记录里。入口在「我的 → 想去清单 → 旅行计划」，**不新增底部主导航**。

- **存储**：独立增量键 `fandazi.trips`（`{ version: 1, items: [...] }`），**不写进 `fandazi.v1` / `fandazi.v2`**；旅行不会新建店铺档案，也不会复制到店记录。删除行程或移出店铺只调整安排，记录、店铺档案、想去清单都不受影响。
- **只引用店铺 id**：每个 stop 保存 `shopId`（`fnv1a32(城市|店名)`）以及展示用的店名 / 城市 / 区域；同一家店可以同时出现在多个行程，重复添加会被拒绝。
- **状态机**：`want` 想去 → `planned` 已安排 → `checked` 已到店，另有 `skip` 跳过。前三种切换只改行程，**不创建、不修改到店记录**；`checked` 只能来自记录表单的「确认到店」保存，不能手动标记。
- **一键带入**：「记一餐」打开现有记录表单，只预填店名 / 城市 / 商圈 / 坐标，金额、评分、热量保持空白并提示「按这次实际填写，不确定就留空」；保存成功后该 stop 才变为 `checked`，记录数 +1，店铺数不变。
- **筛选**：行程内可按区域、日期（含「未定日期」「行程日期内」）、状态、距离（≤1/3/5 km，需真实坐标与中心点）、参考人均（≤¥50/80/120）、菜系、评分（≥4.0/4.5）筛选；无结果给出「清空筛选」引导。距离与人均取真实值，缺失就进不了对应筛选，不估算。
- **地图联动**：「在地图上看」复用现有地图引擎，按行程内 `shopId` 过滤标记、列表与图例（想去但无档案 / 无坐标的店如实不画点或显示暂无数据），可一键退出筛选；地图店铺详情也可把该店加入最近一份行程。
- **按天分组**：同日店铺归到一组，每组标题是日期（未定日期的单独一组），组内可上移 / 下移手动调序，只改同一天内的顺序，到头会提示「已经是当天最前 / 最后一家」。
- **直线距离巡访顺序建议**：点「按直线距离排序」，以当天当前第一家为起点做最近邻排序；界面写明「直线距离，不是道路里程，也不估算行驶时间」，无坐标的店排最后；排序只是建议，随时可用上移 / 下移手动覆盖。
- **每天预计餐饮预算**：每个日期可单独填「当天预计餐饮预算」（正整数，圆整到元），行程头部汇总「预计餐饮 ¥合计（已设 N 天）」；清空即移除该天预算，不编造默认值。
- **必去 / 备选**：每家店可标记「必去」或「备选」，两者单选互斥，再点一次取消；标记只是个人优先级，不参与记录与统计。
- **信息展示**：卡片显示地址（来自最近一次到店记录）、电话（店铺补充信息）、个人评价（最近一次记录备注），并可直接编辑行程内备注；没有的字段显示「暂无」，不猜。
- **旅行内随机选店**：在**当前筛选结果**里随机挑一家并高亮，只用于临场决定，不写到店记录、不改行程状态；没有候选时提示先放宽筛选。
- **空数据**：没有行程时给出「新建旅行计划」入口与说明；没有坐标 / 人均 / 评分的店显示「暂无数据」，距离仍按真实坐标才 Haversine、否则「手填」。
- **备份**：旅行计划段自备份 `schemaVersion` **5** 引入，当前完整备份为 **8**；`payload.trips` 保存完整行程，含每天的 `dayBudget` 与每个 stop 的 `priority`；恢复预览会报告「旅行计划：N 个行程 / M 个地点」。旧备份（v4 及更早）没有该段时保持本机行程不动、不报错；旧 trips 数据缺 `dayBudget` / `priority` 时按空值读取，不丢 stop；`trips` 段结构非法（如 `items` 非数组、stop 缺 `shopId`）整包拒绝，本机数据不变。恢复点同样包含行程，可回滚。
- **界面上限**：最多 100 个行程、每个行程 200 个店铺；375×812 无横向滚动，操作按钮 / 输入命中 ≥44px。

## 备份与恢复

「我的 → 数据」里有两类导出，用途不同：

| 方式 | 包含内容 | 适合 |
| --- | --- | --- |
| 导出 JSON / CSV | 记录字段，**不含照片** | 看数据、导表格、导入到其他工具 |
| **完整备份**（`.fandazi-backup.json`） | 全部记录 + 全部配置 + **全部照片** + 校验值 | 换机、清缓存前留底、整库还原 |
| 分享给好友（`.fanzi.json`） | 可分享的记录，默认不含照片与私人备注 | 给朋友推荐，不是备份 |

### 完整备份

1. 「我的 → 数据」→ **完整备份**，面板会先显示记录条数、照片张数与**预计体积**；
2. 点「生成并下载备份」，浏览器下载到下载目录；APK 内会调起系统分享面板，选「保存到文件」即可；
3. 生成后记下 `fandazi.backup.last`（时间、记录条数、文件大小），「我的 → 数据」会显示「上次备份：X 天前（N 条 / M.B）」；
4. 距上次备份超过 7 天，或自上次备份后新增/修改 ≥10 条记录，「我的」页顶部会出现一条备份提醒（复用应用内提醒条），点「去备份」直达面板。

文件结构（`schemaVersion` 是「备份格式版本」，本版为 8；`payload.version` 是数据结构版本，仍为 3）：

```json
{
  "format": "fandazi-backup",
  "schemaVersion": 8,
  "exportedAt": "2026-11-05T...",
  "checksum": { "algo": "SHA-256", "scope": "canonical(payload+photos)", "value": "…64 位十六进制…" },
  "stats": { "records": 30, "photos": 5, "photoBytes": 29167, … },
  "payload": { "version": 3, "settings": {…}, "blacklist": [...], "wishlist": [...], "votes": [...], "places": [...], "localConfig": {…}, "feedback": { "version": 2, "items": [ { "key": "店铺key", "action": "tired", "surface": "draw", "at": "...", "until": "...", "name": "店名" } ] }, "profile": { "version": 1, "boost": ["粤菜"], "block": ["川菜"], "budgetCap": 120 }, "shopmeta": { "version": 2, "items": { "店铺id": { "updatedAt": "...", "links": [...], "fields": {...}, "location": {...}, "aliases": [ { "shopId": "店铺id", "name": "店名", "city": "上海", "at": "..." } ], "relatedShops": [...], "relatedTo": "店铺id", "dupIgnored": ["店铺id"] } } }, "trips": { "version": 1, "items": [ { "id": "...", "name": "上海周末", "stops": [ { "shopId": "店铺id", "name": "北店", "city": "上海", "area": "徐汇", "status": "planned", "day": "2026-11-07", "note": "" } ] } ] }, "dishes": { "version": 1, "items": [ { "id": "d...", "visitId": "记录id", "shopId": "店铺id", "name": "小笼包", "price": 28, "rating": null, "note": "", "photoIds": [ { "id": "p...", "cat": "dish" } ], "createdAt": "2026-11-05T...", "updatedAt": "2026-11-05T..." } ] }, "records": [...] },
  "photos": [ { "id": "p1", "dataUrl": "data:image/jpeg;base64,…" } ]
}
```

- **校验值**：对「规范化 JSON（对象键排序）后的 payload + photos」计算 SHA-256。导入时先校验，失败直接拒绝，不会写入任何一条记录。Web Crypto 可用时优先用它，`http://` 局域网等非安全上下文自动退到内置纯 JS 实现，两种实现结果一致（已用 `abc` / 长文本做交叉测试）。
- **版本**：备份里的 `schemaVersion` 高于当前应用时拒绝并提示「请先升级应用」；低于当前时走应用已有的迁移路径（旧版记录会被补默认字段）。
- **体积代价**：照片按原来的压缩规则（每张 ≤360px、最多 80 张、总量 >4MB 提示）存成 data URL，base64 以文本内联进 JSON，因此备份体积 ≈ 照片字节数 + 记录文本；照片越多，生成与下载越慢、占用内存越多。预计体积超过 50 MB 时面板会提醒，但仍可继续。
- **照片**：备份会读 IndexedDB `fandazi.media/photos` 里的**全部**照片（包含已删除记录遗留的孤儿照片）；恢复时按原 `photoId` 映射回记录，已存在的同 id 照片不会重复覆盖。导入结果会报告恢复了多少张、多少字节，以及是否有记录引用了备份里不存在的照片。
- **推荐反馈**：`payload.feedback` 保存 `fandazi.feedback` 的 `{version, items, history}` 原样内容（六档档位、可选 `surface`、可选反馈历史）。恢复时整段还原，**不参与「城市+店名+日期」的记录去重**，同一备份重复导入也不会让反馈叠加；「永不推荐」若在黑名单里缺失会被一并补回，保证黑名单优先。旧备份里的 v1/v2 反馈（无 `surface`、无 `history`）可正常恢复，缺失字段按空处理，`items` 一条不丢。
- **旧备份兼容**：不含 `feedback` / `profile` 段的旧备份可以正常恢复，对应数据「保持现状」——本机现有反馈与口味设置不报错、也不清空；只有备份里真的带了该段才会覆盖。恢复结果弹层会分别写明「该备份不含反馈段 / 不含口味设置段，本机保持不变」。
- **口味设置**：`payload.profile` 保存「我的口味」里的手动设置（提升菜系 `boost`、拉黑菜系 `block`、人均上限 `budgetCap`），自动识别的画像是派生数据、不落盘。恢复时按备份原样还原；该段结构非法（如 `boost` 不是数组、`budgetCap` 非数字）会在校验阶段整包拒绝，本机记录与设置均不变。旧恢复点没有该字段时同样保持现状。
- **平台链接 / 补充信息**：`payload.shopmeta` 保存 `fandazi.shopmeta`（第三方平台链接、链接状态与更新时间、用户手填字段及来源，以及第一阶段的 `aliases` / `relatedShops` / `relatedTo` / `dupIgnored` 等可选店铺关系字段）。合并模式按店铺覆盖同 id 条目、其余保留；完整替换按备份原样还原。**旧备份（v3 及更早，或 version 1 的 shopmeta）没有该段 / 没有新字段**时保持本机现状、不清空；该段结构非法会整包拒绝。恢复结果会报告还原了多少家店 / 多少条链接。
- **旅行计划**：`payload.trips` 保存 `fandazi.trips`（行程、stop 及其状态 / 日期 / 备注）。合并模式按行程 `id` 去重、其余保留；完整替换按备份原样还原。**旧备份（v4 及更早）没有该段**时保持本机行程现状、不报错；`items` 非数组、stop 缺 `shopId` 等结构非法会整包拒绝。恢复预览会报告「旅行计划：N 个行程 / M 个地点」，恢复结果会报告 `tripApplied / trips / tripStops`。
- **菜品**：`payload.dishes` 保存 `fandazi.dishes`（菜名 / 参考单价 / 评分 / 备注 / 菜品照片 id）。合并模式按菜品 `id` 合并、其余保留；完整替换按备份原样还原。**旧备份（v5 及更早）没有该段**时保持本机菜品现状、不报错；`items` 非数组、条目缺 `id` / `visitId` / `shopId` / 菜名、id 重复等结构非法会整包拒绝。恢复预览会报告「菜品：N 道」；恢复后会按结果记录剔除孤儿菜品并报告丢弃数量（`dishApplied / dishes / dishesDropped`）。

### 恢复与恢复点

恢复入口是「我的 → 数据」→ **恢复完整备份**，选文件后会先做校验并展示摘要（备份时间、版本、记录/照片/配置条数、合并模式下的可新增/重复/冲突数量），再选择：

| 模式 | 行为 |
| --- | --- |
| 合并（默认） | 按现有规则去重：`城市 + 店名 + 日期` 相同即视为同一条，人均差 ≤10% 也归为同一条；只写入「可新增」，重复与冲突保留本机 |
| 完整替换 | 用备份内容替换当前全部记录与配置，还原备份原样（记录 id、时间、照片映射都保留） |

无论哪种模式，**导入前都会自动把当前数据存成本机恢复点**：

- 存在 IndexedDB `fandazi.media/snapshots`（与应用照片同一个库，只保留**最近 2 份**，超出自动删除最旧的一份）；
- 恢复点保存记录、偏好、黑名单、常用地点、想去、投票、推荐反馈、口味手动设置、平台链接、旅行计划与引导/教程标记，照片**只存 id 引用，不重复占空间**；旧恢复点若没有反馈 / 口味设置 / 平台链接 / 旅行计划字段，恢复时保持当前值不变；
- 恢复点不是长期存档：下一次导入或恢复会把它挤掉；如果导入后误删了照片，恢复点也找不回来（备份文件才是长期底稿）；
- 导入/恢复完成后，结果弹层里有「恢复到恢复前」；「我的 → 数据」也会列出最近 2 个恢复点，可单独恢复。

失败不会出现「导入一半、老数据没了」：流程是**先校验 → 写照片 → 内存里构建新数据 → 原子切换 localStorage（`fandazi.v1`）并回读校验**，任一步失败都会清理本次新写入的照片、保留原数据；失败提示会区分校验失败、版本过旧/过高、照片写入失败、空间不足。

### 常见错误处理

| 提示 | 原因 | 处理 |
| --- | --- | --- |
| 校验失败：文件内容与校验值不一致 | 文件被手改、下载不完整或传输损坏 | 换一份完好的备份；不要用文本编辑器改备份内容 |
| 不是有效的 JSON：文件可能被截断 | 文件只下载了一半 | 重新下载；确认文件以 `.fandazi-backup.json` 结尾且能完整打开 |
| 备份版本 X 高于当前应用支持的 5 | 用新版本应用备份、旧版本应用恢复 | 先升级应用（或换用新版 APK / 在线版）再恢复 |
| 备份文件缺少校验值 | 不是完整备份（可能是普通 JSON / 好友包） | 用「完整备份」生成的文件；好友包请走「导入好友分享」 |
| 照片写入失败 / 空间不足 | IndexedDB 空间不够、被其他标签页占用或无权限 | 清理浏览器存储、关闭其他标签页后重试；原数据不会被改动 |
| 恢复点不存在或已被覆盖 | 又做了一次导入，旧恢复点已被挤掉 | 用备份文件重新恢复；恢复点只保留最近 2 份 |

**未实现**：云备份 / 跨设备自动同步 / 备份加密与密码保护；完整备份文件是本机明文 JSON，请自行保管。恢复点同样只在本机，清浏览器数据会一起消失。定时自动备份已提供但**默认关闭**（「我的 → 本机数据 → 启动时自动备份（仅应用内）」），且只写应用私有目录。

**1.2.0 崩溃修复**：1.1.0 在 Android 16 上启动闪退，原因是启动阶段经 Capacitor 桥接调用 `Filesystem` 写自动备份；1.2.0 把该检查移出启动路径、改成默认关闭的开关，并给所有 `Filesystem` / `Share` 调用加了同步异常兜底，真机已确认可正常启动。

## 推荐反馈（六档）

推荐主卡与两张备选卡底部都有一排轻量反馈按钮，不弹大窗；已反馈的店会在店名下方显示标记（如 `吃腻了·剩 21 天`）。

**统一通道（第二阶段③）**：每日推荐、抽签、盲盒、朋友推荐、聚会推荐、健身推荐、旅行推荐七个入口共用同一套 `applyFeedback()` 与 `feedbackBarHtml()`，写入同一个 `fandazi.feedback`；每条反馈带可选 `surface`（`daily/draw/blind/friend/gather/fitness/trip`）记录来源，只用于文案与历史归因，不改变各场景的预算、距离与偏好权重。反馈条明确提示「只影响推荐排序，不写到店记录」。「想去」是另一类数据（只进 `db.wishlist`），不等于到店；三类互不污染。

| 档位 | 语义 | 生效范围 | 实现 |
| --- | --- | --- | --- |
| 想吃 | 提高该店权重 | 长期 | 正向加成，随时间衰减但不归零（最低约 ×1.12） |
| 可以考虑 | 明确「中性」档 | 长期（权重 ×1.00） | 替换该店之前的正负反馈并记入状态，不新增加权、不写黑名单 |
| 今天不想吃 | 仅本次推荐排除 | 当天 | 内存集合 + 历史留痕；跨天或刷新后恢复，不落长期 items |
| 最近吃腻了 | 短期降权 | 21 天 | 从约 ×0.55 线性回到 ×1.0，到期自动失效，界面显示剩余天数 |
| 不喜欢这家店 | 长期降权 | 长期 | 约 ×0.62 起，按 240 天时间常数缓慢回到 ×1（不归零、不永久、可撤销） |
| 永不推荐 | 加入黑名单 | 永久 | 复用现有黑名单，推荐、抽签、盲盒、聚会与旅行候选都排除；可撤销 |

### 与算法、黑名单的关系

- 打分时在原有评分之后乘上 `feedbackMultiplier(key)`，不改变原有权重公式；**没有任何反馈时严格返回 1.0**，排序与旧版逐项一致（已用同一份数据跑旧版 `index-v11.html` 与新版本对比，0 差异）。
- 优先级从高到低：**黑名单（永不推荐）→ 硬性忌口 → 反馈加权 → 偏好加权**。临时排除、短期降权、永久排除是三种不同机制，不混用。
- 七个入口的卡片都渲染同一排反馈按钮，但聚会 / 健身 / 朋友各自的预算、候选集与排序逻辑不变——统一的是反馈机制与数据，不是把算法做成一套。
- 时间衰减、探索位与推荐解释都保留：反馈只乘在原分数之后，不参与「为什么推荐」的文案生成。

### 存储、历史、撤销与改判

反馈独立存 `localStorage` 的 `fandazi.feedback`，不改 `fandazi.v1`、不改 `db.records`：

```json
{
  "version": 3,
  "items": [
    { "key": "上海|甲味小馆", "action": "tired", "surface": "daily", "at": "2026-11-05T...", "until": "2026-11-26T...", "name": "甲味小馆" }
  ],
  "history": [
    { "id": "fbh...", "key": "上海|甲味小馆", "name": "甲味小馆", "action": "want", "prev": "", "surface": "draw", "at": "2026-10-20T..." },
    { "id": "fbh...", "key": "上海|甲味小馆", "name": "甲味小馆", "action": "tired", "prev": "want", "surface": "daily", "at": "2026-11-05T...", "until": "2026-11-26T..." }
  ]
}
```

- `surface` 为**可选**字段：旧版反馈没有它照常读取；非法值按空处理，不丢弃整条反馈。`history` 同样可选，旧版 `fandazi.feedback` 缺它时按空历史读取，`items` 一条不丢。
- `history` 最多保留最近 300 条，只用于追溯「这家为什么被推荐 / 为什么被降权」，不参与排序；「我的 → 推荐反馈」下方按时间倒序展示最近 10 条。
- **改判**：把某家店换成另一档时写新状态，并在历史里记 `prev`，界面显示「改判自 X」；**撤销**会移除当前档位、权重回到 1，并追加一条 `action:"undo"` 历史（撤回永不推荐时同步移除黑名单）。
- `key` 现阶段沿用现有去重键「城市|店名」（小写）。**v2 迁移时会映射为 shopId**，避免以后改店名、换城市时丢反馈。
- 「我的 → 推荐反馈」可按六个档位筛选、逐条改判、撤销单条、清空全部（清空需二次确认，同时清历史并移除对应黑名单）。
- 撤销单条后分数回到反馈前的整数分，multiplier 回到 1.0（实测浮点误差 0）；「今天不想吃」不落长期状态，刷新即恢复，但历史保留。
- 「可以考虑」不再只做一次性清除：它是一条独立档位（权重 ×1.00），历史里能看到它替换了哪一档。

**未实现**：想吃暂只提高该店本身权重，口味标签级传播留给 v2 画像；没有多设备同步。（反馈含历史已随完整备份/恢复点一起还原，见「备份与恢复」。）

## 口味画像

「我的 → 我的口味」展示一块**自动识别**的饮食偏好画像，并在下方提供手动调整。画像是**派生数据**：只读现有记录、反馈与该店标记，不新增字段、不改 `db.records`，也不要求重新填写任何资料。

### 输入与输出

| 输入（全部来自现有数据） | 输出（自动派生） |
| --- | --- |
| 历史评分与四维评分、到店频次与最近到店时间 | 菜系权重 Top3（如「粤菜 60%」） |
| 人均消费、菜系 `category`、口味标签 `tags` | 口味标签权重 Top3 |
| 想去 / 喜欢标记、六档推荐反馈、常用地点与距离 | 价格带（加权 P20–P80）与距离容忍度（P75） |
| 预算与出行耗时 | 新鲜度偏好：爱回头 / 爱尝新 / 均衡 |

### 可信度阈值（写进代码与文档）

有效记录 = **至少有菜系或口味标签，且能算出人均**；五项字段（菜系 / 人均 / 评分 / 标签 / 四维评分）完整度低于 60% 时降一档。

| 可信度 | 有效记录条数 | 画像对总分的影响 | 界面 |
| --- | --- | --- | --- |
| `low` | < 10 条 | **严格 0**（乘数恒 1.00，等价于没有画像） | 画像区置灰，提示「记录还不够，画像暂不参与推荐」 |
| `medium` | 10–29 条 | 最大 ±8%（乘数 0.92–1.08） | 显示「中等可信」 |
| `high` | ≥ 30 条 | 最大 ±15%（乘数 0.85–1.15） | 显示「高可信」 |

界面始终显示「依据 N 条有效记录 / 共 M 条 · 完整度 X%」。低可信度时**画像乘数严格为 1.0**，排序与无画像逐项一致（实测 0 差异）。

### 优先级（写死）

**永久黑名单 > 忌口 / 排除条件 > 手动口味设置 > 画像加权 > 原有评分**

- 黑名单与忌口在候选过滤阶段先执行，画像只乘在最终分上，**任何画像加权都不能把黑名单店拉回推荐或抽签**。
- 手动设置多于自动结果时以手动为准：手动提升某菜系 ×1.15（低可信度也生效）；手动拉黑菜系、设置人均上限则在推荐与抽签里**直接排除**（不是降权），跳过原因会写进推荐说明。
- 推荐理由会写出依据，例如「符合你的粤菜偏好（自动识别，依据 24 条记录，×1.07）」；手动设置时写「你手动提升了「日料」偏好（手动，×1.19）」。

### 乘数与存储

- `profileMultiplier(shopKey)` 在原有评分之后相乘，与反馈乘数并列；无画像 / `low` / 找不到该店时**严格返回 1.0**。
- 自动画像由五个维度合成亲和度后映射到 ±amp：菜系份额（相对 Top1）、口味标签命中、价格带内外、距离容忍度、新鲜度；缺少数据的维度自动剔除并重新归一。
- 手动设置独立存 `localStorage` 的 `fandazi.profile`，缺失即「无手动设置」：

```json
{ "version": 1, "boost": ["粤菜"], "block": ["香菜店"], "budgetCap": 90 }
```

### 重置语义

「重置为自动」需要二次确认，会清空 `boost` / `block` / `budgetCap` 三项，画像立即回到纯自动识别；重置后的排序与重置前的自动结果完全一致（实测误差 0）。

### 性能与缓存

画像**不是每次推荐都重算**：按需计算一次后缓存，在记录保存、反馈变更、手动设置变更时失效（`invalidateStores()` 同时清空画像缓存）。

1000 条记录实测（headless Chrome）：画像计算 **0.7 ms**，带画像推荐 **2.6 ms**（同数据关掉画像 1.7 ms），抽签 0.8 ms；旧基线分别约 1.6 ms / 3.2 ms，未出现退化。

### 当前未覆盖

- 画像只作用于**每日推荐与抽签**，健身 / 聚会 / 朋友推荐暂未接入，避免改变既有方案排序；
- 口味标签级传播仍待 v2 店铺实体（当前仍按「城市|店名」聚合，改名或换城市会丢历史）；
- 未做画像历史曲线与跨设备同步；`fandazi.profile` 的手动设置已随完整备份/恢复点还原（自动画像不落盘，恢复后按记录重算）。

## 选餐模式与快捷操作

「今天吃什么」顶部有三档模式（A/B/C），各自独立；下面的快捷操作只作用于 A「帮我决定」。

| 模式 | 怎么选 | 状态隔离 |
| --- | --- | --- |
| A 帮我决定（默认） | 评分 + 距离 + 时间 + 画像 / 反馈加权，1 主推 + 2 备选 | 不受 B/C 影响（实测切换前后主推与条件完全一致） |
| B 按我的想法选 | 先选菜系 / 口味 / 预算 / 距离，再**硬筛**，排序仍用原有加权 | 不写入 A 的会话条件，排序规则不变 |
| C 完全随机 | 价格区间内等概率抽一家，抽签动效保留 | 与 A/B 互不影响，只排除不该出现的店 |

### 多样性约束（A 模式）

- 同菜系在 Top3 最多 **2 席**；
- 同商圈在 Top5 最多 **2 席**；
- Top5 至少保留 **1 个探索位**（想去，或 ≥90 天没去过），优先放第 5 席；
- 约束过紧时自动放宽并返回 `relaxed`，不会为了凑规则给空列表；
- 只重排前 5 席，全量分数不变（20 家逐家对比，差异 0）。

实测（20 家：粤菜 10 / 川菜 10，商圈 徐汇 / 静安 / 浦东）：Top3 菜系 粤 2 / 川 1；Top5 商圈 徐汇 2 / 浦东 2 / 静安 1；10 次推荐 **10 次都带探索位**（店14，309 天未去）。

### 推荐理由

每条理由都来自记录与预算本身，不写套话：评分与你记录均值的对比、人均是否在预算内、距离来源（定位 / 手填）与耗时、新鲜度（几周没去）、反馈与画像加权。

实测例子：

- 「评分 4.8，高于你记录的平均 4.4 分」
- 「距你约 1.6 km（手填），步行约 10 分钟（手填估算），约 家 出发」
- 「很久没去（7 周），换个口味」

### 六个快捷操作

全部是**确定性筛选**（不重新随机），执行后条件条会列出当前生效的筛选，并可一键「清除全部」。

| 操作 | 做的事 | 实测（20 家样本） |
| --- | --- | --- |
| 换一家 | 把当前主推加进会话排除集，再重排 | 店2 → 店3 → 店4 → 店5，连续不重复 |
| 换个菜系 | 硬筛指定菜系 | 结果 5/5 全为川菜 |
| 价格再低一些 | 人均上限 = 当前主推 ×0.8 | 70 → 56，结果 40–50 |
| 距离更近 | 上限 = 当前候选距离中位数 ×0.7 | 2.7 km → 1.9 km，结果 1.0–1.9 km |
| 排除最近吃过的 | 只看 7 天前吃过的记录 | 剩余 47 / 309 天 |
| 暂时不考虑这家 | 加入会话排除（仅本次会话） | Top1 立即换店 |

条件只存在内存（`dailySession`），**不写 localStorage**，刷新或重开页面即清空，不改动原有记录与设置。

### C 完全随机 vs 抽签页

两个入口位置不同、算法也不同：

| | 完全随机（今天吃什么 → C） | 抽签（抽签页） |
| --- | --- | --- |
| 抽样 | 严格等概率 `Math.floor(Math.random()*pool)` | 评分 × 新鲜度加权 |
| 排除 | 黑名单、忌口、手动拉黑菜系、超预算、价格区间外 | 同左，另有抽签页自己的区间与抽选筛选（最低评分 / 品类标签 / 现在营业 / 未去时长 / 来源池 / 仅行程） |
| 权重 | 无，不可调整 | 权重表可复核、随机数可复现；同池内尽量避开上一次结果 |
| 动效 | 8 帧滚动名字后定格 | 原有的滚动与揭晓 |

5000 次实测：池 20 家、期望 250、实际 202–289，χ² = 23.9（df = 19，α = 0.001 临界值 43.82），不拒绝均匀性，每家都被抽到。

### 抽选（筛选、计数与持久排除）

抽签页新增「抽选设置」：筛选与「这次不抽」只影响候选池，**不删除、不修改**任何店铺、想去、到店记录或旅行数据。

| 条件 | 口径 | 未知数据怎么算 |
| --- | --- | --- |
| 最低评分 | 不限 / 3.0+ / 4.0+ / 4.5+，只纳入有真实评分的店 | 无评分 = 未知；仅「不限」时参与，开启评分筛选后排除并在计数中说明 |
| 品类 / 标签 | 从现有店铺的 `category` 与 `tags` 动态汇总去重，可多选；命中任一即通过 | 没有品类/标签的想去店在筛选开启时按「标签不匹配」排除；汇总为空时显示「暂无标签」 |
| 现在营业 | 用现有 `openStart/openEnd` 与当前时刻判断，支持跨夜（17:00–02:00） | 无营业时间 = 未知；开启后排除，并在计数里列出「无营业时间 N 家」。`dayType` 在本应用是工作日/周末**场景偏好**，不是营业日历，因此不拿它推断营业，避免虚构 |
| 未去时长 | 不限 / 7 / 30 / 90 天内没去过（按 `lastVisit` 的天数，≥ N 天通过） | 无到店记录的店（含想去清单）视为「从未去过」，符合条件 |
| 来源池 | 全部有档案的店 / 仅想去清单 / 仅收藏 | 「仅收藏」在本应用没有独立收藏集合，实际口径 = 想去清单（应用内「收藏」页签就是想去清单），与「仅想去」同源；全部池按 `shopId` 去重（记录与想去同名同城只算一家） |
| 仅本次行程 | `fandazi.trips` 中状态非 `skip` 的 stop 命中的店；没有带店的行程时点击开关会提示（不会伪造候选） | 应用没有「当前行程」标记，本版口径是**所有旅行计划中未跳过的店**；skip 的店不进池 |

候选计算是只读纯函数 `buildDrawPool(filters)`，返回 `items / total / filteredOut / excludedOut / unknown / reasons`。界面显示「候选 N 家 / 因条件排除 M 家（来源档案 T 家，这次不抽 E 家）」，并单独列出无评分、无营业时间、未填人均的数量；条件开启导致排除时，列出「无评分 a / 无营业时间 b / 标签不匹配 c …」的排除明细。候选为 0 时提供「放宽条件（清空筛选）」；若有持久排除，再提供「恢复全部排除」。

「这次不抽」写入独立增量键 `fandazi.draw`（version 1）：

```json
{ "version": 1, "excluded": ["shopId..."], "filters": { "minRating": 0, "tags": [], "openNow": false, "notVisitedDays": 0, "source": "all", "tripOnly": false }, "updatedAt": "..." }
```

- 只记 `shopId`，不写 `v2.shops` / `v2.visits`，不删除任何数据；
- 设置面板可查看名单、单条「解除」、全部恢复；候选数为 0 且存在排除时提示恢复；
- 筛选条件同步存 `fandazi.draw.filters`，刷新后保留，另有「重置筛选」；
- 坏 JSON / 结构不合法时回退空偏好，不崩。

结果卡动作全部复用既有入口：**记一餐**打开原有记录表单（到店闸门逻辑不变），只预填店名 / 城市 / 商圈 / 坐标，**金额、评分、热量留空**；**加想去**复用想去清单；**看地图**复用既有地图弹层。抽选结果**绝不自动写记录**，必须点「记一餐」再保存。

抽选偏好是本机偏好，**不进入完整备份**（备份 schema 仍为 6）；换设备不会带走「这次不抽」和筛选。

## 数据结构 v2 与迁移

这一版把「一家店多条到访」的数据结构落到本机：新增 `shops` 与 `visits`，旧 `records` 一次性迁移。

迁移引擎、双读路径与界面入口都已落地：所有操作都在「我的 → 数据 → 新版数据」卡片里完成，不需要开发者控制台。下面「迁移入口与安全操作」一节是完整步骤。

### 两个键

| 键 | 内容 | 写权限 |
| --- | --- | --- |
| `fandazi.v1` | 旧结构（`records` + settings 等），迁移后**逐字节冻结** | 迁移后只读，代码里没有任何路径再写它 |
| `fandazi.v2` | `{version:2, migratedAt, shops:{…}, visits:[…], meta:{…}}` | 迁移后唯一的写入目标 |
| `fandazi.migrated` | 迁移标记：时间、店铺数、到访数、孤儿照片数、源记录数 | 读回校验全部通过后才写 |

照片字节不进 localStorage：`visit.photoIds` 只存 IndexedDB 主键，旧 `record.photoId` → `visit.photoIds[0]`。

### 字段表

| shop | 说明 |
| --- | --- |
| `id` | `fnv1a32(城市\|店名)` 的 8 位十六进制；跨设备、跨会话稳定 |
| `name` / `city` / `area` | 取最近一次到访的写法 |
| `address` / `lat` / `lng` | 取最近一次到访；没填就是 `null` |
| `category` / `tags` | 菜系取最近一次；标签取所有到访的并集 |
| `avgPrice` | 各次到访人均的平均值（只统计填过的），缺失为 `null` |
| `note` / `photoId` | 最近一次到访的备注 / 店铺照 |
| `ratingAgg` | 由 visits 重算：`{rating, dims:{taste,env,service,value}, n, visits, latest, lastVisit}` |

| visit | 说明 |
| --- | --- |
| `id` | **复用旧 `record.id`**，因此重复迁移不会产生重复到访 |
| `shopId` | 上面 shop 的 id |
| `date` | 旧 `visitDate`；缺失保留哨兵 `2000-01-01` |
| `dateEstimated` | 日期为哨兵时为 `true`（UI 需说明「日期未填」） |
| `amount` | 实际消费 = 旧 `totalPrice`；**缺失为 `null`，不按人均×人数估算** |
| `people` | 人数，至少 1 |
| `rating` | 旧综合分；缺失为 `null`，不补 0 |
| `dishes` / `wantReturn` | 旧数据里有才写 |
| `note` | 备注 |
| `photoIds` | 照片引用数组 |
| `importedFrom` / `createdAt` / `updatedAt` | 原样保留 |
| `legacy` | 旧记录中上表未覆盖的字段（距离、营业时间、四维评分、来源、标签等）**原样保留** |

`visit.legacy` 是刻意保留的：投影层需要把这些字段原样还原，才能保证下游 0 改动、双读 0 差异。它不属于新结构语义，后续做「店铺级重命名 / 多图」时可以逐步收窄。

### 投影规则（现有功能为什么不用改）

启动时读取顺序：`fandazi.v2` 存在且结构合法 → 用 v2；否则走原来的 v1 逻辑（旧代码原样）。v2 模式下拉起的 `db` 不是原始 v2，而是把 `shops + visits` 投影成旧 `db.records` 形状的兼容视图：

- 店铺级字段（地址、坐标、菜系、店铺照、备注）取**最近一次到访**；
- `record.rating` 取该次 `visit.rating`；店铺聚合评分另存 `shop.ratingAgg`，两者互不覆盖；
- `record.totalPrice` 取该次 `visit.amount`，缺失为 `null`；
- 记录顺序 = visits 顺序，因此 `buildStores()` 的「最近一次」判定与旧逻辑完全一致。

所以推荐、抽签、统计、分享图、导出、备份、巡店、投票、聚会、健身等下游函数**一行未改**。写入统一走 v2：`save()` 在 v2 模式下由当前 `db.records` 重建 `shops/visits` 并只写 `fandazi.v2`；恢复备份 / 恢复恢复点也走同一套（`commitDbNext`）。

### 迁移入口与安全操作

入口统一在 **我的 → 数据 → 新版数据** 卡片，不迁移时界面与旧版完全一致（卡片之外的按钮、列表、统计都没有变化）。

**未迁移状态**：显示「当前使用旧版数据（N 条到访记录）」和三条风险提示——迁移不可自动撤销、旧数据会保留为只读副本、建议先备份再迁移；按钮是「先备份再迁移」和「升级到新版数据」。

**升级步骤**：

1. 点「升级到新版数据」，先出**预览**：`将迁移 N 条 → M 家店 / K 条到访`，预计耗时、`fandazi.v2` 体积与相对 v1 的增量、孤儿照片数（照片引用在 IndexedDB 里找不到的情况），并写明「旧数据（`fandazi.v1`）会以只读副本完整保留」。预览与执行用的是同一个 `v2PlanBuild()`，所以预览数字就是执行结果。
2. 确认后进入忙碌态（按钮立即替换，连点无效；引擎内另有迁移锁兜底）。
3. 完成后面板给：新增到访 / 跳过重复 / 店铺数、总到访与店铺数、耗时、v2 体积、孤儿照片明细，以及「建议立即备份一次」+ 一键备份按钮。备份会带 `payload.v2`。
4. 卡片随即变成「当前使用新版数据（迁移于 <时间>，N 家店 / M 条到访）」，多出「重建 v2」和「回到旧版」两个入口。

**先备份再迁移**：不强制，但一步到位——生成完整备份文件（含照片），显示文件名 / 体积 / 记录数 / 照片数，然后可直接接着预览迁移。

**回到旧版**：二次确认弹窗里显示**实际算出来的** `lostVisits`（v2 里存在、v1 里没有的到访条数，不是写死的文案），另外列出会回退的配置类别（设置、黑名单、想去、投票、常用地点），说明**照片不会丢**，并强调不可撤销。执行后自动刷新，结果面板给：记录数、丢失了多少条、`fandazi.v1` 未被修改、照片仍在、配置已回到迁移前。

**重建 v2**：说明它只重写 `fandazi.v2`，`fandazi.v1` 与 IndexedDB 照片都不动，不会删记录也不会把已不存在的照片补回来；显示当前店铺 / 到访 / 孤儿数、预计耗时。执行后给重建前后的店铺数、到访数、孤儿数对比、耗时、体积和孤儿 id 明细。

v2 模式下**新增 / 编辑 / 删除记录走原有表单，写入的是 `fandazi.v2`**（`fandazi.v1` 全程逐字节不变），刷新与重启浏览器后数据仍在。

### 回退代价（说清楚，不是无损）

「回到旧版数据」只会删除 `fandazi.v2` 与 `fandazi.migrated`，`fandazi.v1` 与照片一直都在。但：

- 迁移后在 v2 模式下**新增 / 修改的记录只存在 v2**，回到旧版会丢失这部分（确认框显示的就是接口返回的真实 `lostVisits`）；
- 设置、黑名单、想去、投票、地点在 v2 模式下写在 `meta.state`，迁移后修改过的内容同样会回到迁移前的状态；
- 因此它是「回到迁移那一刻的底稿」，不是「无损撤销」。

### 孤儿照片

迁移与「重建 v2」时会把所有 `photoIds` 与 IndexedDB 实际主键比对，不存在的记进 `meta.orphanPhotos` 并在结果里给出数量，**不静默丢弃**。孤儿引用仍然留在 `visit` 上（方便之后补图或清理），投影时照常输出 `photoId`，下游只是显示不出图。

### 备份兼容

完整备份的 `payload` 仍是 **v1 兼容结构**（`records` 投影 + settings 等），同时在 v2 模式下追加 `payload.v2 = {shops, visits, meta}`。

- 老版本 / 仍在 v1 模式的设备可以正常读这份备份的 `payload.records`；
- 当前版本恢复时按当前模式落地：v2 模式会依据恢复后的记录重建 v2（`visits` 由 `record.id` 重新生成，`legacy` 保证字段不丢）；v1 模式则保持 v1，之后再点升级；
- 恢复点（IndexedDB `snapshots`）仍存 v1 结构 + 照片 id 清单，恢复时同样走投影，不会出现「备份说能恢复、实际恢复不了」。

## 美食日记

入口在「记录」页顶部的分段控件：**列表 / 日历 / 日记 / 地图**。四个视图共用同一份数据，列表与日历的行为没有改动，日记与地图是新增视图。

### 时间线

- 按 `visit.date` 倒序，按月分组；每个月标题右侧显示**当月餐数与花费小计**（只统计有实付的记录，缺金额会单独标出「N 餐未记金额」）。

### 性能策略

- 分页渲染：首屏只建 **20 条** DOM，底部「加载更多」每次追加 20 条；不会一次建 1000 条。

- 筛选、月份切换只重算内存中的 `visits`，不重复读库。

## 地图视图

入口是「记录」页顶部第四档 **地图**，与列表 / 日历 / 日记共用同一份数据。默认**不是真实地图**：没有瓦片、没有地名、不接任何地图 SDK、不申请 API Key、不发外部请求；打开页面时不会向高德 / 百度 / 任何地图服务发起请求。可选的高德底图同样只在显式选择后才加载（见下文）。

### 画的是什么

- **纯本地投影**：把有 `lat/lng` 的店按等距圆柱投影画到 Canvas，x 用 `cos(平均纬度)` 修正，y 用 `-lat` 保证**北在上**；打开时自动缩放到所有点的范围（四周留 30px）。
- **点的大小与颜色**：图例可在「到访次数 / 综合评分」间切换。到访越多或评分越高，点越大、颜色越深；未评分的店在评分图例里最浅。合并簇在点中央显示数字。
- **无底图的说明**：画布左下角常驻「无底图 · 点由坐标投影」；底图只画浅色经纬网格和比例尺，不画任何虚构街道。
- **不虚构位置**：没有坐标的店**不会**出现在画布上，也不会按商圈中心猜一个点；它们进入「未填坐标 N 家」列表，每行都有「补坐标」按钮，直接打开该店最近一条记录的表单，在「经纬度 lng / lat」处填写，或用「用当前位置填入店铺坐标」。保存后地图立即更新。

### 坐标与距离

| 来源 | 怎么来的 | 地图/列表表现 |
| --- | --- | --- |
| 记录坐标 | 记一餐时手填 `lng / lat`，或用「用当前位置填入店铺坐标」写入同一字段 | 画在图上；距离按 Haversine 实算，标注「定位」 |
| 手填距离 | 记录里的「距离 km」，没有坐标 | 不上图；列表显示「距我约 X km（手填）」 |
| 都没有 | 无坐标、无手填 | 不上图，列表显示「未填距离」 |

- 地图**不会**把「手填 km」换算成坐标，也不会把商圈中心当成店铺位置。
- 只有当你点过「定位我」（或推荐页的「用当前位置」）后，才有「我的位置」基准；店铺坐标与我的位置同时存在才算实距，否则仍按手填值并明确标注。
- 坐标只存在你的记录里，不上传、不写第三方。

### 点选 / 簇 / 定位

- **点标记**：直接打开该店详情（与列表详情同源数据）：地址、综合 / 四维评分、人均、最近到访、距离、坐标、菜系标签，以及最近 6 次到访（点某次可进日记详情）。详情底部是「高德定点 / 百度搜索 / 导航」，全部 `target="_blank" rel="noopener noreferrer"`，只在点击时新窗口打开。
- **簇合并**：屏幕距离 ≤26px 的店合并成一个标记（同坐标必然合并），标记中央显示数量，点开显示簇内店铺列表，再点某家进该店详情。拖动/缩放后会按新位置重新合并，不会出现两个点叠在一起点不中的情况。
- **定位我**：点按钮才调用一次 `navigator.geolocation`（复用原 `locateMe`，超时 10s），成功后画出「我」和 1 / 3 / 5 / 10 km 同心圈，像素半径按当前缩放换算（`km / 111.32 * scale`）。拒绝授权、超时、环境不支持都只提示，地图与已有点不受影响，按钮恢复可再点。
- **缩放 / 平移**：滚轮以鼠标位置为中心缩放，双指捏合缩放，单指拖动平移，右上角有 `+ / − / 复位`。复位回到所有点范围并清空选中。
- **地图 / 列表**：分段切换。列表沿用列表页的搜索、品类、评分筛选，并支持按距离 / 到访 / 评分排序；距离排序把无距离的店放最后，手填距离明确标注「手填」。店铺行点开同样是详情 sheet。

### 可替换底图（将来接真实瓦片只换一层）

代码里底图与画点严格分层：

```js
var MAP_LAYER_ID = 'blank';
var MAP_BASE_LAYER = {
  blank: { id:'blank', draw: function(ctx, view){ /* 只画背景网格 + 比例尺 */ } }
};
```

- `draw(ctx, view)` 只负责背景；`view` 提供 `w / h / scale / project(lat,lng) / unproject(x,y)`。画点、簇合并、命中检测、缩放平移、点选全在 layer 之外，不依赖具体底图。
- 将来接真实底图：在 `MAP_BASE_LAYER` 注册一个新 layer，按 `view.project` 对齐瓦片即可；也可调用 `mapview.setLayer(id)` 切换（内部 `mapSetBaseLayer`）。

#### APK 内高德失败诊断（2026-11-07）

内嵌页失败时不再只有一句笼统提示：地图页错误卡片下方会**自动展开「诊断明细（可直接截图）」**（`#mapDiag`），并带「复制明细」按钮。明细把失败分成三层，逐层给证据：

| 层 | 判定依据 | 明细里能看到 |
| --- | --- | --- |
| 网络层：内嵌页 HTML 未到 | `iframe.onload` 未触发（15 秒 × 2 次） | 内嵌页完整 URL、每次耗时、`__fandaziTest.mapview.layer().embed.diag.html='timeout'`，以及原生 HTTP / 跨域探测的可达性结论 |
| 脚本层：HTML 到但高德脚本未到 | 收到 `page-start`/`ensure-start`，但 20 秒内没有 `script-loaded` | 高德脚本完整 URL、脚本状态（未开始 / 下载中 / 超时）、阶段打点（内嵌页耗时 / 宿主耗时 / 第几次尝试） |
| 注册层：脚本到但未注册 AMap | 收到 `script-loaded`，未收到 `amap-ready`，或 `fz:diag` 回传错误码 | 高德真实错误码（如 `INVALID_USER_DOMAIN`）、诊断请求的 HTTP 状态 / `content-type` / 耗时 |

- **iframe 到底有没有跑到**：宿主在 `iframe.onload` 后向 `contentWindow` 发 `fz:ping`，内嵌页回 `fz:pong` 自带 `href / host / document.referrer / referrerPolicy`；再加内嵌页执行时的第一条 `fz:trace`（`page-start`）。三样都对不上就说明 HTML 都没到，而不是高德脚本报错。
- **Referer 修正**：旧版 iframe 带 `referrerpolicy="no-referrer"`，会把内嵌页发往 `webapi.amap.com` 的 Referer 一并剥掉；高德按域名白名单校验时可能因此判失败。本版移除该属性，恢复默认策略（只发来源域名），明细里同时显示 `document.referrer` 与策略，便于和顶层打开对照。
- **顶层对照入口**：错误卡片新增「直接打开地图页」按钮，用同一个 `map-embed.html` 在顶层打开（APK 内由 Capacitor 交给系统浏览器），绕过 iframe。若顶层能出图、iframe 不能，问题就在 iframe/WebView 这一层；内嵌页单独打开时右下角也会显示同样的阶段与真实请求结果。
- **实测**：CDP `.tmp/amap-embed-diag-test.js` **5/5**（连接挂起 → 网络层；只有 `page-start` → 脚本层；回传 `INVALID_USER_DOMAIN` + HTTP 200 / 123 ms → 注册层）。注意：无真机时只能验证宿主与内嵌页的判定逻辑，WebView 的实际 Referer / DNS / 证书行为仍需真机截图确认。

#### APK 内高德「脚本未就绪」误判修复（2026-11-07）

真机诊断显示：内嵌页自己已打印 `amap-ready`（宿主记录 145ms，早于 `iframe-load` 的 301ms），但宿主仍在 20 秒后报「高德脚本在 20 秒内仍未完成加载（已重试 1 次）」。

- **真因**：`iframe.onload` 处理里无条件重开了一条「等待就绪」计时（`mapEmbedTimeout('ready')`），而就绪消息在 `load` 之前就已到达并处理；`load` 之后重开的计时器 20 秒后触发时，`mapEmbedTimeout` 没有「已就绪」终态守卫，于是把成功改写为超时，并触发 `?_fzr=1` 重试，第二次再复现一次，最终报「未完成加载」。**不是网络问题，不是消息名不一致，也不是 `event.source` / origin 校验误拒**——诊断面板能打印 `amap-ready` 就证明消息已收到且校验通过，监听也在 `load` 之前就已绑定。
- **修法**：① 消息监听在创建 iframe / 设置 `src` 之前绑定；② `mapEmbedReadyNow()` 只在首次就绪时落终态，此后任何 `load` / 计时回调 / 重试都不得清空；③ `f.onload` 先查 `amapState.embedReady`，已就绪则直接返回，不再挂新计时；④ `mapEmbedTimeout()` 入口加终态守卫；⑤ 三条成功信号等价（`fz:script-ready` / `fz:trace:amap-ready` / `fz:pong.amap===true`），并在未就绪时每 1.2 秒补 `fz:ping`；⑥ 内嵌页 `fz:pong` 增加 `amap / map / v:3` 字段，便于识别缓存里的旧内嵌页；⑦ 首次成功时同时清掉内存与 `localStorage['fandazi.mapAmapErr']`，设置卡不再展示历史失败文案。
- **回归**：`.tmp/fixtures/embed-early.html` 精确复现真机时序（`page-start` 立即、`script-start` 15ms、`amap-ready` 130ms、不发 `fz:script-ready`，用 `?_fzd=280` 把 `iframe-load` 推到约 300ms）；断言 `readyBy='trace'`、`retry=0`、`stage≠ready-timeout`、不回落、容器可见且 `fz:init` 已送达、无超时文案。`.tmp/fixtures/embed-pong-only.html` 验证就绪消息完全丢失时的 ping/pong 兜底。`amap-embed-wait-test` **12/12**、`amap-layer-test` **23/23**、`p0-test` **28/28** 全部通过。
- **仍未验证**：本机无真机，WebView 内的实际拖动 / 缩放手势、真实高德瓦片渲染效果仍需真机确认；自动化只证明「判定成功后容器可见、尺寸非 0、`fz:init` 已下发」，不能替代真机手感验收。

#### 若 APK 内 JS API 仍不可行：两条路径的成本对比

前提结论：**网页版已正常**，说明 Key、`securityJsCode`、`violetz10032.github.io` 白名单都没问题；故障范围只剩 APK 的 WebView/网络层。若真机诊断明细最终显示「内嵌页 HTML 未到」或「注册层错误码」，按下面两条选：

| 方案 | 前置条件 | 成本 / 改动 | 适合场景 |
| --- | --- | --- | --- |
| A. 把 `map-embed.html` 部署到国内可达的 HTTPS 托管（推荐） | 一个可访问的域名（大陆 CDN 需备案；香港/海外托管免备案但速度一般）+ 把该域名加进高德 Key 白名单 | 托管约几元～几十元/月；代码只改 `mapEmbedUrl()` 一处；现有 iframe / 降级 / 诊断全部复用 | 想保留高德底图，又不想接原生 SDK |
| B. 接入高德 Android 原生地图 SDK | 控制台新建 **Android 平台 Key**，绑定包名 `com.fandazi.app` 与固定签名 SHA1；CI 改用固定 keystore（放 GitHub Secrets，构建时解码） | 固定签名证书 SHA1：`EA:43:76:8B:2A:90:7F:09:B2:2D:A7:10:FE:C0:1B:BE:F4:38:34:E7`（对应本地 `android-app/signing/fandazi-release.p12`，密钥不入库）；需新写原生插件桥接标记/相机/点击，APK 体积增加数 MB，保留画布兜底 | 必须离线/原生性能，或域名托管不可行 |
| C. 主页面直接加载高德脚本（去掉 iframe） | 主页面源必须是白名单内域名；APK 主页源固定为 `https://localhost`，而高德不接受 `localhost` | 结论：**当前不可行**，除非把整个应用页面迁到白名单域名（等于方案 A 的代价） | 不推荐 |
| D. APK 只用画布 + 手填坐标 | 无 | 已可用，零成本 | 地图只是辅助、能接受无底图 |

> 选 B 时，用户只需在高德控制台填：**包名 `com.fandazi.app`**、**SHA1 `EA:43:76:…:34:E7`**；然后把这个 keystore 的 base64 放进 GitHub Secrets（`ANDROID_KEYSTORE_BASE64` / `ANDROID_KEYSTORE_PASSWORD` / `ANDROID_KEY_ALIAS=fandazi` / `ANDROID_KEY_PASSWORD`），CI 侧再加解码与 `signingConfig` 即可。以上“固定签名 + Secrets”尚未接线，属于选 B 后的第一步。

### 已知限制

- 默认没有真实底图与地名，只有点、网格、比例尺；勾选「高德」后才有街道底图（需要联网、受配额限制）。地图页本身不提供搜索；店铺定位的搜索与选点在**记一餐表单**里（网页版可用，APK 内随高德图层状态而定，见「店铺定位」一节）。
- 高德模式下底图由官方 JS API 渲染，Canvas 只叠加标记；若关闭浏览器对高德的网络访问，底图会是空白网格而标记仍可见（符合协议与降级设计）。
- 高德与画布是两套投影，切层时会按当前点重新拟合视图，因此切换瞬间视野可能有轻微变化，但不会改变任何记录坐标。
- 簇合并是**屏幕像素阈值**（26px），缩放越大越容易拆开；没有做服务端/网格索引级别的聚合。
- 定位只在点击按钮时取一次，不做持续跟踪；「我」的位置是上一次定位缓存（`fandazi.geo.last`）。
- 未填坐标列表最多渲染前 60 家、地图列表最多渲染前 300 家（计数始终是真实总数），其余需用搜索或筛选定位。
- 坐标精度取决于你填写/定位的质量；本版不做地址解析，也不根据店名反查坐标。

## 统计口径

入口是「我的 → 统计」。所有数字都从本机真实记录现算，不缓存派生统计值、不写新的存储键；年份与月份选择只存在内存（`statsState`），刷新回到默认（最近有记录的年份 + 全年）。

### 好友导入默认不计入

- 好友 `.fanzi.json` / 分享包导入的记录带 `importedFrom`，默认 `statsExcluded:true`，**不进统计、排行榜与年度报告**（金额、次数、偏好都不算）。
- 导入预览里的「计入我的统计」复选框默认不勾；旧分享包没有该字段时同样按「不计入」处理。
- 「我的 → 统计」顶部有「统计口径」开关：勾选把全部好友导入记录设为计入，取消则全部排除；统计与年度报告立即重算，只改 `statsExcluded` 标记，不改记录内容。
- 已归档的年度快照保持生成时的口径，不随开关回溯改写；单条记录的显式标记在批量切换时会被统一覆盖。

### 红线：金额只认实付

- 只有 `totalPrice > 0` 的到访才算「有金额」；0、空、负数都记为**未记录**。
- **绝不用「人均 × 人数」或其他方式推算缺失金额**；不做插值、不按菜系均值补全。
- 每个金额区块都标「样本 N 笔 / 缺失 M 笔」，缺失的到访**不进总额、不进平均每次、不进平均人均的分母**。
- 页面顶部常驻说明：「金额只用真实记录，缺失不按人均推算」。

### 金额指标

设所选范围（年 / 年+月）内到访集合为 `R`，有金额的子集为 `A = {r | totalPrice(r) > 0}`：

| 指标 | 公式 | 边界 |
| --- | --- | --- |
| 花费 | `∑ totalPrice(r), r ∈ A` | `A` 为空显示「—」，不显示 0 元 |
| 金额样本 / 缺失 | `n = |A|`，`miss = |R| - |A|` | — |
| 平均每次 | `∑ totalPrice / n`，四舍五入到元 | `n = 0` 显示「—」（不是 0，不是 Infinity） |
| 平均人均 | `∑ totalPrice / ∑ people(r), r ∈ A`；人数空/0 按 **1** 人 | 同上；分母是**有金额笔数的人数之和**，与缺失笔数无关 |
| 到访笔数 | `|R|` | 与金额无关，缺金额也计数 |

`R` 只包含**日期可解析**的记录（空日期 / `2000-01-01` 哨兵 / 标记为估算日期都排除）；日期未知的记录见文末「日期未知」。

### 餐厅指标

按 `城市 + 店名` 聚合为「一家店」（同名不同城市分开；同城同名视为同一家）。

| 指标 | 口径 |
| --- | --- |
| 到访次数 Top 10 | 全部记录按到访次数降序；同次数按最近到访日期新→旧，再按店名。金额缺失不影响排序（次数是真实计数） |
| 最近到访 10 家 | 有日期的店按 `lastDate` 降序取 10；右侧显示 `statsAgo`：「今天 / 昨天 / X 天前」，无日期的显示「日期未知」 |
| 最常光顾 | 只在「最近 90 天内有到访」的店里取次数第一；同次数取最近到访更近的。若 90 天内无到访，显示「最近 90 天未去过」，并补一句全部记录第一是谁 |
| 最值得再光顾 | 候选：平均评分 ≥ 4.0 **且**有最近到访日期；得分 `score = 平均评分 × 距今天数`，取最大。天数越大代表越久没去，评分越高代表越值得，两者相乘偏向「高分但久未光顾」；页面同时展示算式（如 `4.2 × 77 天 = 323.4`） |
| 个人评分最高 | 只取**到访 ≥ 2 次**且评分非空的店，按平均评分降序（同分取次数多的），避免一次高分的偶然 |

### 偏好指标

| 指标 | 口径 |
| --- | --- |
| 最常吃菜系 | 按 `category`（空值归入「未分类」）计数，展示前 5；占比 `pct = count / 全部记录数 × 100`（保留 1 位小数）。**分母是全部记录**，含未分类与日期未知，所以各项占比加起来可能不足 100% |
| 口味标签 Top 8 | 每条记录的 `tags` 去重后各计 1 次，按次数降序取 8；同一标签在多条记录里出现就累加 |
| 逐月饮食变化 | 以所选范围的最后一个月为终点，向前取 6 或 12 个月；每月按菜系统计条数，堆叠柱状图（SVG 自绘）。只画当月出现过的菜系中总数前 4 的系列，其余合并为「其他」；柱高按当月总餐数，最大值为纵轴上限，纵轴 0/中/最大值三档刻度 |
| 场景消费 | 按 `scene` 分组（日常 / 聚会 / 健身 / 工作日午餐等，取值用现有 `SCENE_LABEL`；空值显示「未标注」），降序按餐数，再按金额。每行显示 `N 餐 · 均 ¥X`（均值只对有金额的笔数），缺失单独标「M 笔未记录」 |

### 消费指标

| 指标 | 口径 |
| --- | --- |
| 月度 / 年度消费 | 顶部 `年份` + `月份` 两个下拉（月份含「全年」）；花费、平均每次、平均人均、到访笔数随之切换。年份列表来自有记录的年份并补当前年，避免空年 |

### 交互与明细

- 年份 / 月份切换即时重算；「近 6 月 / 近 12 月」分段按钮也即时切换。
- 任一统计行可点开明细：菜系 → 该菜系全部到访、标签 → 含该标签的到访、店铺 → 该店全部到访、月份 → 该月全部到访、场景 → 所选范围该场景的到访。明细复用日记的 `diaryRow` 与详情，最多列 80 条（超出注明总数）。
- 明细顶部同样标「N 餐 · 有金额 X 笔（共 ¥Y）/ 未记录 Z 笔」。

- 统计页本身不直接出长图；年度长图见下一节「年度报告」。

## 年度报告

入口在「统计」页顶部的「生成年度美食报告」。年份可选，默认当前年；报告与长图只统计所选年份中**日期已知**的记录，日期未知的记录不进入年度报告。

### 计算口径

| 指标 | 公式 / 口径 |
| --- | --- |
| 年度到访次数 | 该年记录条数 |
| 不同餐厅数 | 按「城市 + 店名」去重后的店铺数 |
| 最喜欢的菜系 | 该年菜系出现次数最多的一个；占比 = 该菜系次数 / 该年总次数，保留 1 位小数 |
| 到访最多餐厅 | 按店聚合，到访次数最多；并列时取最近到访更晚的一家 |
| 最高评分餐厅 | 店铺平均评分最高，且该店到访 ≥ **2 次**（排除单次偶然；单次高分店只可能出现在「最满意的一餐」） |
| 年度消费总额 | 只累加 `totalPrice > 0` 的真实金额；`n` = 有金额笔数，`miss` = 缺失笔数 |
| 平均每次 | 总额 / **n**（有金额笔数），不是 / 总次数 |
| 最满意的一餐 | 单条记录评分最高；并列取日期更晚；展示店名 / 日期 / 评分 / 人数 / 评价，记录有照片则显示照片 |
| 月度到访与消费 | 固定 12 个月；每月次数与真实金额之和。缺失金额的月份不画消费条并写「未记录」，0 次的月份显示「—」 |

### 年度报告存档

报告默认仍是**实时派生**：每次由 `records` 按自然年重算。想让某一年的数字"钉住"，可以在报告页把它存档。

- **一年一份**：独立键 `fandazi.reports`，结构 `{version, items:[{year, archivedAt, calcVersion, stats, highlight}]}`；同一年再次存档即**覆盖**，覆盖前弹出「已有 2026 年存档（存档于 X），覆盖后旧数字不可恢复」二次确认。
- **只存聚合**：`stats` 保存到访次数、餐厅数、消费总额 / 样本 / 缺失 / 均次、最喜欢菜系（名 / 次数 / 占比）、到访最多、最高评分、首末日期、12 个月次数与金额；**不存整份记录**。
- **最满意一餐**只存必要副本：店名、日期、评分、评价文字、人数、`photoId` 引用。**不复制照片二进制**；渲染时按 id 去照片库取，取不到就显示「照片已缺失（存档只保存引用，原图不在本机）」。
- **口径版本**：`calcVersion` 当前为 1。旧版本的存档在界面标「旧口径」，点「用当前口径重新生成」会走覆盖确认；不会静默改数。
- **界面**：年份选择器上有存档的年份标「（已存档 · MM-DD）」；打开已存档年份默认显示**存档数字**，横幅写明「存档快照 · 存档于 2026-11-05 · 共 N 条记录」，可切「看实时（当前记录）」对比；实时视图会提示「本年已有 M-DD 的存档」并可切回。
- **操作**：存档这一年（先预览数字与"存档后固定"说明）、覆盖存档（二次确认）、删除存档（二次确认）、导出存档 CSV（19 列）。长图按**当前显示的那份**生成，标题与页脚分别标「存档快照 / 实时数据」，文件名带 `-存档`。
- **空白年不存档**：该年 0 条记录时按钮禁用，确认与直接写入都会被拒绝。

### 备份口径

- **实时报告**不落盘、不缓存；**存档**落在独立键 `fandazi.reports`，因此完整备份的 `payload` 现在包含 `reports` 段（键列表：`version / settings / blacklist / wishlist / votes / places / gathers / reports / localConfig / feedback / profile / records`）。
- 恢复规则：备份带 `reports` 段时，`replace` 整段还原、`merge` 按年份保留本机并补齐备份里的年份；**备份不含该段（旧备份 / 旧恢复点）时保持本机现有存档，不覆盖、不报错**，恢复结果写明 `reportsApplied=false`。
- 恢复点（`fandazi.meta` 里的本地快照）同样带 `reports`，用恢复点回滚会把存档一起回滚。
- 导出 JSON 带 `reports`；CSV 另有「导出存档 CSV」（19 列：年份、存档时间、口径版本、次数、店数、总额、样本、缺失、均次、菜系、菜系次数、菜系占比、到访最多、最高评分、最满意店 / 日期 / 评分、首末日期）。
- 实测备份往返：造 1 份存档 → 完整备份 → 清空 → 恢复 → 全部数字一致；旧备份（手工删除 `reports` 段）→ 恢复 → `reportsApplied=false`，原存档保留。
- 年份选择器由 `annualYearList()` 从记录、当前年份与存档年份动态生成（非硬编码），后续加「跨年合并」或「报告模板」不需要改计算层。
- **不支持**：跨年合并报告、导出 PDF、存档页查看店铺明细（存档只存聚合，店铺清单仅实时视图有）、跨设备实时同步；存档只保留「最满意一餐」的 1 张照片引用，其余照片不随存档保存。

## 多人聚餐活动

「聚会」面板下的**聚餐活动**：把「一群人吃什么」从口头讨论变成可复核的候选清单 + 投票 + 一次记录。全程本机运行，**没有服务器、没有实时同步**。

### 流程

1. **建活动**：标题（可空，默认「X 月 X 日聚餐」）、日期、时间、人数、人均预算（区间或上限）、区域（区/商圈）或距离半径；场景固定为「聚会」。
2. **参与者**：名字可只填「我 / 朋友1」；每人可选忌口标签（不吃辣 / 不吃海鲜 / 素食 / 不吃牛羊肉 / 不吃香菜，可自定义）、偏好菜系、是否吃辣。**不填参与者**也能按人数直接估算。
3. **生成候选**：硬性过滤后按「共同偏好命中数 → 评分 → 距离 → 新鲜度」排序，取 3–8 个（可调），每个候选给出中文理由与「哪几位参与者能吃」。
4. **投票**：复用现有候选卡图 + 二维码 + 两段文本；候选编号按生成顺序稳定输出，投票记录按活动保存在 `db.gathers`。
5. **回填与排序**：按「总票数」或「每人票数」手动回填；实时显示排序、并列标记与当前生效的平票规则。
6. **结算 → 确认到店**：结算只把活动标记「已完成」并锁定胜出店，**不写日记**；之后点「确认已到店，写入日记」才生成 1 条记录（场景 `friends`、人数取活动人数、金额留空）。投票结果本身不算一次到访，避免「选了但没去」污染统计。

### 忌口硬过滤（不是软偏好）

任一参与者命中以下任意一条，该店直接**排除**，不进入排序：

| 关卡 | 规则 |
| --- | --- |
| 黑名单 | 店名在黑名单中 → 排除（黑名单优先于一切） |
| 预算 | `人均 > 预算上限`（按活动的上限或区间上界）→ 排除 |
| 忌口 | 参与者忌口关键词命中「店名 + 菜系 + 标签 + 商圈」→ 排除（如「不吃辣」命中 `川/湘/辣/火锅/烧烤…`；「素食」只匹配荤食词，**素食餐厅不会被素食者排除**；「不吃牛羊肉」命中 `牛/羊/肉/烤肉…`） |
| 区域 | 填了区域且店不在该区 → 排除；填了半径且距离超过半径（或距离未知）→ 排除 |
| 营业时间 | 活动时间不在营业时段 → 排除（打烊） |

排除项在详情里以「已排除 N 家」折叠列出，每家写明「谁因为什么被排除」。

### 空结果与一键放宽

候选为 0 时给出具体、可执行的建议，并可直接点按钮放宽：

- `人均预算提到 ¥35 可多 1 家`（取被预算挡住的最低人均）
- `放宽 1 位参与者中的「不吃辣」可多 1 家`（逐条忌口统计）
- `取消区域「浦东」限制可多 7 家` / 放大半径可多 N 家

数字都由同一套过滤函数重算，不是手写文案。

### 平票规则

票数相同时按以下顺序依次比较，**界面会写明本次实际用的是哪一条**（如「票数并列 → 按人均低」；全部相同显示「完全并列」）：

1. 人均更低
2. 距离更近
3. 评分更高
4. 到访间隔更长（更久没去优先）

### 结算口径

- **先结算、后到店**：结算只锁定胜出店并把活动标记「已完成」，`recordId` 为空，日记与统计均不变；点「确认已到店，写入日记」才 `+1` 条记录。
- 记录：`visitDate = 活动日期`、`people = 活动人数`、`scene = friends`、`category = 候选菜系`、综合评分与四维评分留空、备注含「聚餐：<标题>」。
- 金额：**一律不预填**（`totalPrice = null`、`perPrice = null`）——参考人均只写在备注里（「参考人均 ¥X，实际金额未填，可到记录里补」），不进入实际消费统计；没有人均时备注「金额未填，可到记录里补」。
- 结算后活动状态改为「已完成」，可在活动列表「已完成」分组回看；未确认到店的会显示「尚未写入日记」和确认按钮。

### 存储与备份（为什么选 `db.gathers`）

- 聚餐活动存进**现有整包 `db.gathers`**（v1 随 `fandazi.v1`，v2 存 `meta.state.gathers`），**没有新增任何 `localStorage` 键**。理由：完整备份、恢复点、JSON 导出都是按整包序列化的，放进 `db` 即自动带走；不新增键也避免旧版本读不到、换机漏数据。
- `migrate()` 缺 `gathers` 段时按空数组处理；旧备份（无该段）恢复不报错、活动为空、记录不受影响；合并模式按活动 `id` 去重。
- 「活动 CSV」单独导出 19 列汇总（标题/日期/时间/人数/预算/区域/状态/候选数/胜出店/票数/记录 id 等），带 BOM，Excel 直接打开。
- **不支持**：跨设备实时投票、活动内聊天、多人同时编辑；投票仍是「生成卡图/二维码 → 群内投 → 手动回填票数」。

## 风格皮肤（P3 蓝 / P4 黄 / P5 红）

三套皮肤**全部是可选皮肤，默认不启用**。默认外观仍是上一节的浅色 / 深色 / 跟随系统；不选皮肤时，变量与样式与原版完全一致。视觉 3.0 起分段按钮改名为 **Warm / Cream / P3 / P4 / P5**（`none` / `cream` / `p3` / `p4` / `p5`），并新增预览卡、当前标识与「恢复默认外观」，见下文「视觉 3.0」。

### 入口与开关

- 位置：「我的 → 外观」。第一行仍是明暗三档（**浅色 / 深色 / 跟随系统**）；其下是「风格皮肤」分段按钮 **Warm（默认）/ Cream / P3 / P4 / P5**，再下面是预览卡、「恢复默认外观」与「减少纹理」开关。
- 皮肤自带默认明暗：**P3 默认深色、P4 默认浅色、P5 默认深色**。选中皮肤时只把 `fandazi.theme` 写成对应值，之后仍可用上面三档自由切浅 / 深，甚至「跟随系统」。
- 存储：皮肤独立键 `fandazi.skin`（`none` / `cream` / `p3` / `p4` / `p5`），纹理独立键 `fandazi.skinTexture`（`on` / `off`，默认 `on`）；明暗继续由 `fandazi.theme` 管。这些键都**不写入 `fandazi.v1` / `fandazi.v2`**，不改变备份结构。
- 首屏防闪：`<head>` 内联脚本在渲染前同时写入 `data-theme`、`data-skin`、`data-skin-texture`，刷新不会闪回默认配色。
- 非法值（例如手改成 `fandazi.skin = "p9"`）在读取时一律回落 `none`，不抛错；无该键的老用户读到的就是 `none`，外观与行为不变。

### 实现方式

- 只在 `html[data-skin="px"]` 与 `html[data-skin="px"][data-theme="dark"]` 上覆盖一层 CSS 变量，**没有重写任何样式结构**；形态修饰只有少量规则（标题斜切角度、卡片圆角与边缘、按钮形状、图表配色、地图画布配色）。
- 新增三个语义令牌，并把原有强调色的用法迁到令牌上（只改引用，不改布局）：
  - `--accent`：填充色（按钮底、进度条、图表主色）；
  - `--accent-text`：强调**文字**色（链接、分数、选中态文字），保证与底色 ≥ 4.5:1；
  - `--accent-ink`：画在 `--accent` 填充上的文字色；
  - `--border-strong`：功能性边框（输入框、次按钮），与所属底色 ≥ 3:1。
  - 默认主题下 `--accent-text` 等于原 `--accent`、`--accent-ink` 为白色，所以不选皮肤时观感逐像素不变。
- 地图画布所有取色走 `mapThemeColor`（`--map-*` 变量），切皮肤 / 切明暗时**立即重绘**，不用等下次进入地图。
- 分享图与分享长图**固定浅色品牌配色**，不随皮肤变化——不会分享出去一张红黑或荧光黄的图。
- 图表颜色改为读 `--chart-1..6` 变量，默认值与原图表配色一致，皮肤下自动换色。

### 纹理（全部程序生成，零外部图片）

不引入任何图片文件、base64 位图或网络资源；所有纹理由 CSS 渐变 / 内联 SVG / Canvas 生成：

| 皮肤 | 纹理 | 参数 | 落点 |
| --- | --- | --- | --- |
| P5 红 | 半调网点 | `radial-gradient` 平铺，网点透明度 6% / 5% | 仅静态 `body` 背景，不铺在正文文字后 |
| P4 黄 | 水平扫描线 | `repeating-linear-gradient`，1px 间隔，透明度 ≤4% | 仅静态 `body` 背景 |
| P3 蓝 | 低频噪点 + 环状光晕 | 内联 SVG `feTurbulence`（`baseFrequency` 很小、低 opacity）+ `radial-gradient` | 仅静态 `body` 背景 |

- 性能红线：`feTurbulence` 只挂在静态背景层，**不挂在列表项、滚动容器、地图画布**等会频繁重绘的元素上；地图画布只在 `mapDraw` 里绘制，不叠 CSS filter。
- P5 斜切 ≤8°（标题 `skewX(-6deg)`），半调只作纹理；P3 只用抽象圆 / 环；P4 扫描线极淡。

### 减少纹理与自动降级

- 「我的 → 外观 → 减少纹理」开关写入 `fandazi.skinTexture`；关闭后只保留配色与切角，去掉网点 / 扫描线 / 噪点。
- 尊重 `prefers-reduced-motion: reduce`；低端设备（`navigator.hardwareConcurrency <= 4` 或 `navigator.deviceMemory <= 4`）在**用户没有显式设置过**的情况下自动降级为关闭纹理，并弹一次提示 + 在开关旁写明原因（仍可手动开启）。
- 用户显式开 / 关过之后，自动降级不再覆盖用户选择。

## 视觉 3.0：token 收口 / Cream Editorial / 主题中心 / 动效

这一轮把视觉从「一组能用的变量」收成**三层 token + 5 套设计语言 + 一个主题中心 + 一套可关闭的动效**。审查报告与完整规范见 [`docs/theme-spec.md`](docs/theme-spec.md)。

### 三层 token

| 层 | 位置 | 覆盖内容 |
| --- | --- | --- |
| 基础层 | `:root` | 颜色（含地图 / 图表 / 语义状态色）、间距 `--sp-1..6`、字阶 `--fs-xs..2xl`、行高 `--lh-tight/base/loose`、字体 `--font-ui/--font-display`、圆角 `--r-card/--r-btn/--r-tag/--r-field/--r-modal/--r-sheet/--r-toast`、阴影 `--shadow/--shadow-1/--shadow-2/--shadow-btn/--shadow-modal`、动效 `--dur-fast/--dur-base/--ease` |
| 明暗层 | `html[data-theme="dark"]` | 只覆盖颜色与阴影，不改形状与间距 |
| 皮肤层 | `html[data-skin="..."]` + `[data-theme="dark"]` | 只覆盖颜色 / 字体 / 圆角 / 阴影，再叠加少量形态修饰；不改 DOM |

公共组件已接入：按钮（`.btn/--r-btn`）、卡片（`--r-card/--card-pad/--gap-card`）、表单（`--r-field`）、弹窗（`--r-modal/--shadow-modal`）、抽屉（`--r-sheet`）、空态 / 加载态 / 错误态（语义色 token）、轻提示（`--r-toast`）。token 之外的硬编码颜色从 3 处（`@keyframes flash` 高亮环、输入框聚焦环、盲盒 / logo 阴影）降为 **0 处**（分享图与长图的固定品牌色按设计保留，它们不随主题变化）。

### Cream Editorial（新增第 4 套皮肤）

不是换色，是独立排版语言：奶油纸底 `#F6F1E7`、砖红 `#9B4526`、**衬线标题**（`--font-display` 换成宋体系）、2px 直角、无阴影、顶部 2px 细线、行高放宽到 1.8、字距 1.2px，纹理是极淡的纸纹横线。深色版是「夜间纸张」`#12100D`。

### 主题中心

- **预览**：5 张预览卡，色块直接取 `SKIN_META` / `SKIN_ACCENT`，不写死颜色。
- **切换**：预览卡与分段按钮走同一个 `setSkin()`；切换会套用该皮肤默认明暗。
- **当前标识**：预览卡显示「当前」，`#themeNow` 一行写明「皮肤 · 明暗 · 纹理 · 动效」。
- **恢复默认**：皮肤 `none`、明暗 `auto`、纹理 `on`、动效 `mid`；**不重置任何业务数据**（实测切换 4 套皮肤前后，除主题键外的 `fandazi.*` 键逐字节一致）。
- **持久化**：`fandazi.theme` / `fandazi.skin` / `fandazi.skinTexture` / `fandazi.motion` 四个独立键；`<head>` 内联脚本在首屏前套用 `data-theme/data-skin/data-skin-texture/data-motion`，刷新与重开不闪白、自动恢复。

### 动效（适中）

- 只用 `transform` 与 `opacity`：页面转场 `viewIn`、卡片按压 `scale(.996)`、收藏按钮 `fav-pop`、抽签 / 纯随机结果卡 `resultPop`、盲盒（既有摇动）、旅行随机选中卡 `pop-in`。
- 关闭方式：`fandazi.motion = reduced` → `html[data-motion="off"]` 把动画 / 过渡压到 0.01ms；系统 `prefers-reduced-motion: reduce` 且用户未显式选「适中」时自动生效；页面切到后台由 `visibilitychange` 写 `data-page-hidden`，`animation-play-state:paused`。

## 架构收口（第二阶段⑥）

这一轮不是加功能，是把重复绑定、定时器泄漏与「只写日志」的失败分支清掉，并让文档与代码对齐。

- **事件监听**：交互全部走 `document` 上的委托（`click` / `input` / `change` / `keydown`）与 `window` 上的 `resize` / `popstate` / `focusin`，页面切换（`showView`）不再重复绑定；`homeUIInit()`、`blindBallInit()`、地图指针事件只在启动时绑一次。用 CDP `DOMDebugger.getEventListeners` 实测：连做 10 轮「切页 + 开关行程 / 重复扫描 / 合并预览 / 打卡表单」后，`window` 10 条、`document` 12 条，增长为 0。
- **定时器**：盲盒转速、等待计时、嵌入地图 ping 都自带 `clear`；本轮新建的 `setInterval` 全部被清掉。饭点提醒的 60s 轮询与通知判定遇到 `document.hidden` 直接跳过，回到前台由 `visibilitychange` 补一次，不再后台空转。
- **无重复委托**：反复切页后，一次反馈只写 1 条历史、一次收藏只加 1 家店，不会双写。
- **失败分支统一可见**（不再只 `logError`）：
  - 主库 `save()` → 「保存失败：本机存储空间不足」
  - 收藏写入 → 「收藏保存失败：本机存储空间不足」，并回滚内存状态
  - 推荐反馈 → `saveFeedbackStore()` 返回布尔，失败用 `fbSnapshot/fbRestore` 回滚并提示「反馈保存失败」
  - 旅行 → 「空间不足，旅行计划未保存」
  - 菜品 → 「空间不足，菜品未保存」
  - 一周菜单 / 预算 / 锁定 → 「一周菜单保存失败 / 预算保存失败 / 锁定失败」
  - 食材新增 / 移除 → 「食材保存失败」/「移除失败：…食材仍保留」（不再把存储失败误报成「请先填写食材名称」）
  - 初始化失败 → 「「在家吃」/ 盲盒 初始化失败，部分功能可能不可用」
  - 合并失败逐键回滚并提示；撤销前比对，数据已变动就拒绝并保留现状
- **文档与代码对齐**：`README.md`（本文件）、`docs/framework.md`（新增第 11 节，记录独立增量键、反馈 v3、合并迁移、旅行多站点、监听器/定时器/失败提示的实际实现）、`docs/features.md`（功能表按实际状态更新），并把过期的「云同步未完成」改成「同步为备份级 Gist / Contents / WebDAV，账号体系与多人实时投票仍未做」。

实测（`.tmp/arch-audit-test.js`）**5/5**：监听器零增长、interval 零残留、单次操作只生效一次、四类写失败均有可见提示且内存回滚、正常交互 0 异常。回归：`feedback-test` 0 FAIL、`feedback-v3-test` 19/19、`home-week-test` 18/18。

## 数据与隐私

- 记录存 `localStorage`（键 `fandazi.v1`；升级后为 `fandazi.v2`），推荐反馈存 `fandazi.feedback`，店铺平台链接 / 补充信息与关系标记存 `fandazi.shopmeta`；照片与最近 2 份恢复点存 `IndexedDB`（`fandazi.media`），主题偏好另存 `fandazi.theme`（`light|dark|auto`），语音同意状态另存 `fandazi.voiceConsent`，跨设备同步的 Token / 同步元数据另存 `fandazi.sync.token`、`fandazi.sync.meta`，**默认不上传、不注册账号、无后端**。
- 语音输入是唯一例外：首次使用需用户主动勾选同意，识别时这段音频会交给浏览器内置的云端语音服务转文字；识别结果只进入当前输入框，不自动保存、不随记录上传。不同意则完全不启动识别。
- 跨设备同步也是可选例外：只有你主动开启并点「立即同步」时，才把记录**加密后**上传到你自己的私有 Gist；口令不落盘，Token 只存本机。
- 数据只在这台设备的这个浏览器里：换浏览器、清缓存、换设备都会丢，建议定期「我的 → 数据 → 完整备份」（含照片）。
- 应用不抓取任何平台数据；外部链接仅在用户主动点击时跳转，且不带渠道参数。
- 营养与热量为历史记录估算，**不构成营养或医疗建议**。
- 导出与好友分享会把数据带出本机，导出前请确认是否包含隐私内容；分享包默认不含照片与私人备注。

## 已知限制

1. 出行耗时、营业时间仍为手填；距离对「有坐标 + 点过定位」的店是实算，其余仍是手填估算，可能与实际有偏差。定位只在点击时取一次，不查实时营业状态。
2. 首次离线使用必须先联网打开一次（Service Worker 需要一次在线安装）。
3. iOS 不支持本项目使用的浏览器通知，应用内提醒条仍可用。
4. 无后端，因此没有多人实时投票与云备份；跨设备同步是可选手动功能（加密私有 Gist），不是后台自动同步。
5. JSON 含照片时体积显著增大；1000 条记录导出长图约 84 页，低内存设备可能较慢。完整备份把照片内联为 base64，50 MB 以上会明显变慢。
6. 完整备份与恢复点均在本地；跨设备同步为**可选**功能（加密私有 Gist），需自备 Token 与口令，只同步记录、不含照片 / 想去清单 / 地点 / 设置 / 投票；恢复点只保留最近 2 份。
7. 推荐反馈只作用于每日推荐与抽签；聚会 / 健身 / 朋友推荐未接入；「今天不想吃」只在当天内存生效，刷新后恢复。
8. 快捷操作条件只存在内存，不落盘；多样性约束只在 A 模式生效，B 按条件硬筛时不重排菜系 / 商圈；C 完全随机不接画像与反馈加权（这是它与抽签页的根本区别）。
9. 日记的月份箭头只在「有记录的月份」之间跳转，无法用箭头走到完全没有记录的月份（空月份状态实际由筛选组合触发）；日记暂不支持按月批量导出、批量编辑和年月跨度的自定义区间，筛选条件也不落盘（刷新回到全部）。
10. 地图没有真实底图、地名与道路，也不能点图选地址；簇合并按屏幕像素阈值（26px）而非地理网格；定位只取一次、「我」的位置来自上次缓存；未填坐标列表与地图列表分别最多渲染 60 / 300 行（计数仍是真实总数）。
11. 主题只有浅色 / 深色两套固定配色，不支持自定义主题色；分享图、长图与图标固定浅色，不随主题变化。
12. 语音输入只有网页 / PWA 在线识别：需要 **HTTPS（或 localhost）+ 麦克风授权**，识别时音频会上传到云端语音服务；APK / Android WebView 多数不提供 Web Speech，入口会按能力探测自动隐藏；Safari / iOS 不支持，真机识别质量未验证。
13. 行程分享包与记录分享包一样**无签名校验**，无法证明来源；重复导入同一份行程会多出一份行程副本（店铺始终不重复建档，也不覆盖原有档案）；导入撤销只在本次打开期间有效。
14. APK 内高德图层已在自动化里验证「判定成功 → 容器可见、尺寸非 0、`fz:init` 已下发」，但 WebView 内的真实拖动 / 缩放手感与高德瓦片渲染效果仍需真机验收；内嵌页缓存旧版本时以 `fz:pong` 的 `v:3` 字段识别，未升级的内嵌页可能拿不到兜底 ping 的 `amap` 字段。
15. 重复店铺识别只能处理「店铺聚合键不同」的店；同名同城但实际是不同分店（如「老王面馆」两家店）会先被现有 `城市|店名` 聚合键合成一家，无法在档案页拆开。合并后目标店的地址 / 坐标取「最新一次到访」，可能随并入记录变化；需要固定坐标请用档案页「改坐标」或平台链接补充里的定位。
16. 重复识别是启发式：POI 相同最可靠；无 POI 时名称 + 地址 / 200 米坐标只是候选，仍可能误报或漏报，最终以人工确认为准。关联 / 忽略只写 `shopmeta`，不参与同步包与好友分享包。
